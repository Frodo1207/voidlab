# VOIDLAB Daily News Ops

这个 Skill 用来把 VOIDLAB 的“每日资讯运营”封装成一句话可触发的 Agent 工作流。

它不是只负责“抓资讯”，而是把下面这些动作串成一条链：

1. 获取最近 24 小时资讯
2. 生成站内文章
3. 为文章生成配图
4. 上传图片到服务器
5. 回写文章封面
6. 发送飞书群消息

适用场景：

- 用户说“发今天日报”
- 用户说“跑一轮每日资讯”
- 用户说“把今天资讯发到站里并发群”
- 用户说“同步今天的 AI HOT 到网站和社群”
- 用户说“收集今天资讯并发送到飞书群”
- 用户说“生成文章并把图片一起传上去”
- 用户说“发今天资讯，顺便带封面图”
- 用户说“文章和配图一起生成”

不适用场景：

- 只是查询今天 AI 圈发生了什么，但不需要运营动作
- 只是改一篇已有文章的文案
- 只是单独发飞书消息，不涉及每日资讯链路
- 只是调试前端页面或后台页面
- 只是单独做一张海报，不涉及每日资讯发布

## 目标

这个 Skill 的目标不是只“收集新闻”，而是执行完整的每日资讯运营链路：

1. 从 AI HOT 获取最近 24 小时精选资讯
2. 触发 VOIDLAB 每日资讯任务
3. 生成站内文章草稿
4. 发布到网站
5. 生成每篇文章对应的封面图
6. 上传图片到服务器并回写 `cover_url`
7. 生成并发送飞书群日报

默认执行方式：

- **全自动**
- 默认尝试执行 `采集 -> 审核 -> 发布 -> 生成图片 -> 上传图片 -> 回写封面 -> 群发`
- 如果用户明确说“先别发”“先给我看一下”“先只采集”，则退化为半自动

## 触发判断

命中下面任一表达，就应该优先使用这个 Skill：

- “发今天日报”
- “跑一轮每日资讯”
- “收集并发布今天资讯”
- “把 AI HOT 发到站里”
- “发到飞书群”
- “今天的资讯同步一下”
- “今天的资讯配图也一起做”
- “文章和图片一起上传”
- “生成封面再发”

如果用户没有明确说明是“只采集”还是“全流程”，默认按全流程执行。

## 固定依赖

执行时优先复用这些现有能力：

- 内置 `aihot` Skill：获取最近 24 小时精选资讯
- 项目已有每日资讯后端接口：`/api/v1/daily-news`
- 项目已有文章系统：`articles`
- 项目已有文章更新接口：用于回写 `cover_url`
- 本地图片生成能力：优先复用当前 Agent 能直接生成图片的能力，而不是要求用户手工出图
- 项目已有上传能力或媒体存储：把生成图片上传到 VOIDLAB 可访问地址
- 项目已有飞书发送配置：服务端环境变量中的飞书机器人配置

如果当前项目里已经有每日资讯 API，就不要另起一套独立脚本；优先把 Skill 作为“运营入口”，而不是重复造系统。

如果当前项目里已经有图片上传或媒体接口，也不要再发明第二套临时存储方案。

## 标准执行顺序

### 阶段 1：确认意图

先判断用户这次要的是哪一种：

- `collect-only`：只采集
- `collect-publish`：采集并发布站内
- `publish-with-covers`：采集、发布、生成图片并回写封面
- `full-run`：采集、发布、生成图片、回写封面、群发

默认：

- 如果用户说“跑一轮”“发今天日报”“同步今天资讯”，按 `full-run`
- 如果用户说“生成文章并带图”，至少按 `publish-with-covers`

### 阶段 2：获取资讯源

先使用 `aihot` 获取最近 24 小时精选资讯。

规则：

- 默认使用精选池，不抓全量池
- 默认窗口是过去 24 小时
- 普通日报默认取 5 条左右
- 不凭模型记忆补新闻

如果只是执行项目内每日资讯 API，而 API 已经会自行采集，也可以把 `aihot` 作为验证与摘要参考，而不是重复造内容。

### 阶段 3：触发项目内每日资讯任务

优先调用项目当前已有的每日资讯接口，而不是手工拼凑文章：

- `POST /api/v1/daily-news/collect`
- `POST /api/v1/daily-news/:date/approve`
- `POST /api/v1/daily-news/:date/publish`
- `POST /api/v1/daily-news/:date/send`

执行原则：

1. 先采集
2. 再读取任务状态
3. 如果是全自动模式，继续审核
4. 再发布
5. 再处理图片
6. 最后发群

如果任务已经存在：

- 不强制重复采集
- 优先读取现有任务并继续执行后续步骤

### 阶段 4：站内文章运营

站内文章默认走现有 `articles` 体系。

Skill 不应重新定义文章结构；应沿用系统当前规则：

- AI HOT 精选作为来源
- 最多生成 5 篇文章草稿
- 内容使用 Markdown
- 发布后由官网资讯页展示
- 已发布文章优先补齐封面，再做分发

如果用户说“只发日报，不要站内文章”，才跳过发布环节。

### 阶段 5：图片生成与上传

这是这个 Skill 的新增重点。

规则：

1. 每篇已发布文章都应该尝试生成一张对应配图
2. 配图生成不是单独入口，而是每日资讯链路的内部步骤
3. 生成成功后，要上传到 VOIDLAB 可访问地址
4. 上传成功后，要通过正式接口把图片地址回写到文章封面字段，例如 `cover_url`
5. 如果图片生成失败，不应阻塞整篇文章发布；但必须明确告诉用户哪些文章缺图

默认思路：

- 输入：文章标题、摘要、日期、来源名、栏目语气
- 输出：文章封面图 URL
- 目标：让站内文章、分享图、飞书分发都具备可复用封面

执行要求：

- 优先使用当前 Agent 本地可用的图片生成能力
- 不要求用户每次单独提供图
- 风格应保持统一，优先专业、正式、适合资讯栏目的封面
- 不把图片生成做成“每次手工海报设计”
- 如果项目里已有图片模板或固定风格，应优先复用模板

如果用户明确说：

- “这次不要图”
- “先只发文章”
- “图片后补”

则允许跳过本阶段。

### 阶段 6：回写文章封面

图片上传成功后，应执行正式文章更新流程，而不是直接操作数据库。

原则：

- 通过现有文章更新接口回写 `cover_url`
- 不直接改线上数据库
- 不在 Skill 中硬编码某篇文章 ID
- 回写后应再次读取文章，确认封面字段已生效

如果当前项目还没有合适的文章封面更新接口：

- 应先报告“接口缺失”
- 然后建议补正式接口
- 不要默认改数据库顶替

### 阶段 7：飞书群分发

默认目标是服务器已配置的飞书群，不在 Skill 里硬编码群 ID、密钥或域名。

规则：

- 优先复用服务器环境配置
- 飞书消息中的文章链接必须指向 VOIDLAB 站内地址
- 如果飞书机器人未配置、权限不足或未入群，应明确报告阻塞点
- 不要把密钥写进 Skill，也不要在响应里回显 Secret

如果群发失败：

- 报告失败
- 不要伪装成已成功发送
- 提醒用户检查机器人权限、群成员关系和服务端环境变量

如果用户要兼顾“群里阅读”和“复制到微信”：

- 可以发送阅读版消息
- 也可以附带一条裸链接版文本
- 但这属于分发格式层，不应影响文章和图片的主链路

## 可执行协议

为了让这个 Skill 真正可落地，执行时按下面这条固定协议走，不要只停留在抽象描述：

`collect -> draft -> top-up -> approve -> publish -> generate-covers -> upload-assets -> bind-covers -> build-digest -> send-feishu`

如果用户没有特别说明，默认把这条协议跑完。

## 阶段输入输出

### `collect`

输入：

- 目标日期，默认北京时间今天
- 条目目标数量，默认 `5`

动作：

- 优先调用 `POST /api/v1/daily-news/collect`
- 读取返回任务中的 `items` 和 `article_ids`

输出：

- `task.date`
- `task.items`
- `task.article_ids`
- 当前条目数

### `draft`

输入：

- `collect` 生成的 daily-news 任务

动作：

- 默认复用 daily-news 服务生成站内文章草稿
- 不单独再发明第二套文章生成脚本

输出：

- 草稿文章列表
- 每篇文章的 `id / slug / title / summary`

### `top-up`

这一步专门解决“精选池不足 5 条”的问题。

输入：

- 当前 `items`
- 目标数量，默认 `5`

动作：

1. 如果精选池已满足目标数量，直接跳过
2. 如果精选池不足，使用 `aihot` 的全量池补位
3. 只补当前任务里不存在的条目
4. 通过正式接口 `POST /api/v1/daily-news/:date/items` 追加，不直接碰数据库

输出：

- 补齐后的 `items`
- 最终文章数量

规则：

- 默认最多补到 `5`
- 不重复 `item.id`
- 不重复 `source_url`
- 不覆盖用户已审核过的已发布任务；若任务已发布但用户要求重跑，应先走 `reset`

### `approve`

输入：

- 已补齐的 daily-news 任务

动作：

- 调用 `POST /api/v1/daily-news/:date/approve`

输出：

- 任务状态变为 `approved`

### `publish`

输入：

- 已审核任务

动作：

- 调用 `POST /api/v1/daily-news/:date/publish`
- 让文章正式进入站内 `published` 状态

输出：

- 已发布文章列表
- 站内正式链接：
- `https://voidlab.club/insights/<slug>`

### `generate-covers`

输入：

- 每篇文章的 `title`
- `summary`
- `source_name`
- `date`
- 可选栏目风格

动作：

- 为每篇文章至少生成 `1` 张封面图
- 默认先生成横版封面，适配文章分享和飞书展示
- 如果图片能力允许，可额外生成方图，但不是首版硬要求

默认输出规格：

- 主图：`1200x630`
- 可选补充图：`1080x1080`

输出：

- 本地图片文件路径或生成后的图片二进制
- 文章 ID 与图片产物的一一对应关系

规则：

- 同一篇文章只对应一组固定封面
- 风格默认统一，不逐篇手工设计
- 如果图片生成失败，记录失败文章并继续后续文章，不阻塞整批发布

### `upload-assets`

输入：

- 本地已生成的图片文件

动作：

- 优先走项目正式媒体上传接口，而不是直接拷贝服务器目录
- 当前项目优先使用：
- `POST /api/v1/media/upload`

输出：

- 每张图对应的公网 URL
- 可选 `media_id`

规则：

- 上传成功后必须拿到稳定可访问 URL
- 不把临时本地路径当最终结果

### `bind-covers`

输入：

- 已发布文章
- 图片上传后的 `cover_url`

动作：

1. 先读取文章当前详情
2. 合并 `cover_url`
3. 用正式文章更新接口写回

推荐接口顺序：

- `GET /api/v1/articles/:id`
- `PUT /api/v1/articles/:id`

输出：

- 已绑定封面的文章列表
- 未成功绑定的文章列表

规则：

- 只改必要字段
- 保留原 `title / slug / status / content / source_url`
- 不直接操作数据库

### `build-digest`

输入：

- 已发布文章
- 每篇文章标题、摘要、链接

动作：

- 生成一版适合飞书阅读的“介绍 + 链接”摘要
- 生成一版适合复制到微信的纯文本裸链接摘要

输出：

- `feishu_reading_text`
- `feishu_copy_text`

推荐结构：

- 开头一句总说明
- 每篇文章 1 句介绍
- 每篇附站内链接

### `send-feishu`

输入：

- 阅读版摘要
- 裸链接版摘要

动作：

- 优先调用项目当前已有的 daily-news 发送能力
- 如果当前发送器只支持一种消息体，则至少保证先发一版裸链接可复制文本
- 如果项目后续支持双发，则默认：
- 先发阅读版
- 再发裸链接版

输出：

- 发送状态
- 飞书 `message_id`

## 默认产物

每次 `full-run` 应默认产出四类结果：

1. 站内已发布文章
2. 每篇文章已上传的封面图
3. 一份飞书阅读版摘要
4. 一份微信可复制裸链接摘要

缺任何一类，都不应默认为“全流程成功”。

## 失败与降级

执行时遵循下面的降级顺序：

### 情况 1：精选池不足 `5`

- 允许从 AI HOT `mode=all` 补位
- 补位后继续走主链路

### 情况 2：图片生成失败

- 文章照常发布
- 飞书照常可发
- 但结果中必须明确：
- 哪些文章缺图
- 是否需要后补

### 情况 3：上传失败

- 不把本地图片路径当结果
- 已上传成功的继续回写
- 失败项列出，等待重试

### 情况 4：封面回写失败

- 不回滚已发布文章
- 明确列出未绑定成功的文章 ID 和 slug

### 情况 5：飞书发送失败

- 不影响站内文章和图片产物
- 应直接返回：
- 飞书失败原因
- 是否可以稍后重试

### 情况 6：用户要求重跑当天内容

- 如果当天任务已存在且用户明确要求重跑，应先调用：
- `POST /api/v1/daily-news/:date/reset`
- 再重新执行主链路

## 默认消息模板

阅读版建议结构：

```text
VOIDLAB 今日资讯 | YYYY-MM-DD

1. 标题
一句介绍
https://voidlab.club/insights/slug

2. 标题
一句介绍
https://voidlab.club/insights/slug
```

微信复制版建议结构：

```text
VOIDLAB 今日资讯 | YYYY-MM-DD

1. 标题
https://voidlab.club/insights/slug

2. 标题
https://voidlab.club/insights/slug
```

规则：

- 飞书里用站内链接，不发外源链接
- 裸链接必须直接显示 `https://...`
- 不把“可点击富文本标题”当作唯一分发格式

## 实现优先级

如果用户要分阶段落地，优先顺序如下：

1. `collect -> draft -> top-up -> approve -> publish`
2. `generate-covers -> upload-assets -> bind-covers`
3. `build-digest -> send-feishu`

也就是说：

- 先保证站内内容闭环
- 再保证图片闭环
- 最后补齐飞书分发体验

## 自动化策略

默认自动化模式：

- 自动采集
- 自动审核
- 自动发布
- 自动生成图片
- 自动上传图片
- 自动回写封面
- 自动群发

只有在下面情况时才停下来问用户：

- 飞书配置缺失
- 每日资讯接口不可用
- 图片生成能力不可用
- 图片上传接口不可用
- 文章封面回写接口不可用
- 用户明确要求先预览
- 出现高风险覆盖动作

如果用户说：

- “先看一下”
- “先别发”
- “只采集”
- “只生成草稿”
- “先不要图”
- “图片我自己补”

则必须切换为人工确认模式，不要自动发群。

## 输出要求

每次执行完后，输出应尽量短，但必须包含：

- 本次运行模式
- 每日任务日期
- 是否采集成功
- 是否生成文章
- 是否已发布
- 是否已生成图片
- 是否已上传图片
- 是否已回写封面
- 是否已发飞书群
- 如果失败，失败在哪一步

示例：

- `daily news run: full-run`
- `date: 2026-10-11`
- `collect: success`
- `articles: 5 drafts -> published`
- `covers: 5 generated -> uploaded -> bound`
- `feishu: sent`

如果失败：

- `daily news run: full-run`
- `date: 2026-10-11`
- `collect: success`
- `publish: success`
- `covers: failed at upload`
- `feishu: failed`
- `reason: upload api unavailable / bot missing permission / article cover update failed`

## 边界

这个 Skill 当前不负责：

- 自己直接发明新的资讯正文体系
- 替代后台文章编辑器做复杂人工润色
- 管理多群分发策略
- 手工逐张精修海报
- 长周期周报/月报编排

如果用户后面要把它升级成：

- 多群发送
- 多栏目运营
- 周报月报
- 多风格自动封面
- 图库策略 / 模板策略 / AI 生图策略切换

应在这个 Skill 基础上继续扩展，而不是另起一个同义 Skill。

## 推荐使用风格

- 把它当成“运营动作入口”
- 用一句自然语言触发
- 默认执行今天这一轮
- 默认把图片也一起处理
- 失败时明确卡点
- 成功时给出简短状态回执

## 一句话理解

这个 Skill 代表的是：

**“让 Agent 像运营同事一样，帮你把今天的 AI 资讯从采集、发站、出图、上传到发群一口气跑完。”**
