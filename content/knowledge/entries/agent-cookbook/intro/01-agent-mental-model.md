## LLM 是大脑，Agent 让大脑指挥手脚

这个比喻很贴：LLM 就是“大脑”。它能理解输入，也能给出看起来挺像样的回答。

但问题在于，大脑光会想还不够。要让它真的把事情做完，就得让它能指挥“手”和“腿”去动：读文件、写文件、查数据、发请求、生成一个页面、把结果保存下来。中间靠的不是一句口头禅，而是一套结构化的指令：明确下一步要做什么动作、用什么参数、结果应该回到哪里。

![LLM 通过结构化指令指挥执行与工具](knowledge-asset://3)

## 大脑之外，Agent 还多了什么

只靠 LLM，拿到的更多是“它说得很像”。有了 Agent，开始拿到“过程 + 结果”。最常见的几块东西是：

- 目标：这次到底要完成什么，不是随便聊两句
- 工具：能不能查、能不能写文件、能不能调 API、能不能进数据库
- 状态：当前做到了哪一步，用户刚刚确认了什么，哪些信息已经收集过
- 输出：结果要落到哪，是一段话、一个文件、一个表，还是一个可复用的产物

会发现，Agent 的重点不是“它会不会说”，而是“它能不能把手脚动起来，把事情做完，并且下次还能再跑一遍”。

## 任务环境：用 PEAS 把边界说清

工程里做 Agent，第一件事通常不是写提示词，而是先把它处在什么环境里说清楚。一个常用的办法叫 **PEAS**：把任务环境拆成四个部分：性能度量（Performance）、环境（Environment）、执行器（Actuators）和传感器（Sensors）。

![PEAS：Performance / Environment / Actuators / Sensors](knowledge-asset://4)

拿“旅游路线规划 Agent”来举例，可以这样理解：

| 维度 | 这意味着什么 |
| --- | --- |
| Performance（做得好不好） | 行程是否可执行、是否符合预算/时间、是否覆盖偏好、是否把关键风险说清楚 |
| Environment（外部世界） | 航班/高铁/酒店/地图信息会变化；价格和余票会波动；用户需求可能补充或修改 |
| Actuators（能动手做什么） | 调用搜索/票价/地图 API；读写文件；写入数据库；生成行程页面或文档 |
| Sensors（能看到什么） | 用户输入；API 返回；数据库里已有的历史记录；上一轮行动的结果 |

这个表的价值是：它逼着设计者先回答一个现实问题——“到底从哪里拿信息、能做哪些动作、最后怎么判断做得好”。这些不明确，Agent 往往只能停留在“看起来像”的层面。

## Agent Loop：为什么它不是一次性做完

Agent 之所以需要“循环”，是因为真实环境很少一次就把信息给全：

- 常见情况是“只看得到一部分”。比如查票价，拿到的是某个 API 返回的部分数据，而不是全世界所有航司的实时座位。
- 很多结果也不稳定。两次相邻调用返回的价格、余票可能不一样。
- 环境里还有别的行动者：其他用户的预订行为、系统的动态调价，都在改变环境状态。
- 任务通常是序贯的：当前一步的选择，会直接影响后面能不能做下去。

所以 Agent 的基本运行方式不是“一次性生成答案”，而是循环推进：拿到新信息 → 决定下一步 → 做动作 → 看结果 → 再决定下一步。

![智能体循环：感知→思考→行动→观察](knowledge-asset://5)

## 结构化指令：把想法翻译成动作

从“会说话”到“能做事”，中间最大的差别就是：输出里要能带出明确动作，让系统去执行。很多框架会把一次交互拆成三段：**Thought / Action / Observation**（名字不重要，关键是结构）。

![Thought / Action / Observation 的一次循环](knowledge-asset://6)

一个最小例子可以长这样：

```text
Thought: 先确认出发地、日期、预算。如果预算不明确，就先追问。
Action: ask_user("从哪里出发？预算大概多少？")
Observation: 用户回答：从上海出发，预算 2000 元，两个人。
```

这里的重点不是“Thought 写得多漂亮”，而是 **Action 必须清楚**：调用哪个动作、参数是什么。外部系统执行完动作，再把结果整理成 Observation 反馈回来，下一轮循环继续用。

## 为什么它不是“模型 + 人设”

很多人把 Agent 理解成“模型加个角色设定”，比如“你是资深产品经理”“你是旅游达人”。这种东西能让语气更像，但并不会让系统更能干活。

真正让它从聊天变成做事的，是两件事：

- 给它可以执行的动作（工具）
- 让它把过程留在一个可追踪的状态里（状态/记忆），最后把结果落成产物（输出）

没有工具、没有状态、没有输出落点，很多时候就算叫 Agent，也还是一个“更会聊的模型”。

## 用身体的比喻理解

- LLM：大脑，负责理解、决策、生成下一步
- 结构化指令：大脑到手脚的“神经信号”，把想法翻译成可执行动作
- 工具 / 执行器：手和腿，负责真的去做（读写文件、调 API、查 DB）
- 状态与输出：系统做过什么、做到哪、结果放哪，不然只会“聊完就没了”

## Agent 和工作流有什么区别

如果你把“自动化”都算进来，很容易混在一起。

- 工作流：步骤通常是固定的，更多是“按顺序跑”
- Agent：步骤可以根据输入变化，更多是“先想清楚下一步该做什么，再去做”

简单说，工作流像流水线，Agent 更像一个会根据情况做决定的工人。当然，一个成熟系统里，经常是 Agent 来做决定，决定完再把某一步交给工作流去跑。

## 用旅游规划举个例子

同样是“帮我规划周末杭州旅行”：

- 只有 LLM：大概率直接给你一份看起来很像样的行程，但很多条件是它猜的
- 有 Agent：它会先追问关键条件（时间、预算、出发地、偏好），再用工具去查信息或读取本地资料，最后把行程按结构写出来，甚至落成一个文件或页面

“旅游路线规划 Agent”这个实战章节，就是把这一套组装过程走通：让它不只是写得像，而是真的能跑、能改、能复用。
