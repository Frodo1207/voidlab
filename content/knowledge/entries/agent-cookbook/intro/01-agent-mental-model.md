## 一句话结论

零基础开发 Agent，先学共同骨架，比先学框架名字更重要。因为框架会变、宿主会换、API 会升级，但一个 Agent 到底有没有被设计清楚，最后都要回到同一组问题：目标、输入、工具、状态、输出、验收。

## 这一章要讲什么

- 目标：Agent 为什么而工作
- 输入：它允许读到什么
- 工具：它能动什么
- 状态：它如何记住过程
- 输出：它最终交付什么
- 验收：怎么判断它做对了

## 为什么这一章是全书总纲

如果上一章解决的是“什么东西才叫 Agent”，那这一章解决的就是另一件更实在的事：**一个 Agent 到底应该被设计成什么样。**

零基础最常见的问题不是不会写代码，而是脑子里没有一张稳定的设计图。于是你会看到：

- 一会儿想先写 prompt
- 一会儿又去研究工具调用
- 一会儿又觉得要不要先加记忆
- 最后越做越像“往一个模糊系统里不停塞能力”

这也是为什么这章要把所有东西压成 6 个槽位。因为只要这 6 个槽位清楚，后面无论你换成 `Codex`、`Trae`、LangGraph，还是自己手写最小 Agent，判断标准都不会乱。

## 先看一遍这 6 个槽位

| 槽位 | 它回答的问题 | 如果没想清楚会怎样 |
|---|---|---|
| 目标 | 这次到底要完成什么 | Agent 会很勤奋，但不知道该往哪走 |
| 输入 | 它允许看什么材料 | 容易乱读、串料、边界失控 |
| 工具 | 它能动什么外部能力 | 只能空谈，无法推进任务 |
| 状态 | 它如何记住上下文与过程 | 做到一半就失忆、断流、重来 |
| 输出 | 它最终交付什么 | 结果模糊，不知道产物长什么样 |
| 验收 | 怎么判断它这次做得对不对 | 没法复盘，也没法稳定迭代 |

这张表里最重要的一点是：**这 6 个槽位不是概念清单，而是一张排障图。** 后面你只要发现一个 Agent 不稳定，几乎都能回到这 6 个槽位里定位问题。

## 1. 目标：先回答“这次到底要成为什么结果”

目标不是主题，也不是方向感，更不是一句“帮我处理一下这个”。目标必须能落成一个结果。

比如下面这两句，差别很大：

- 不好的目标：`帮我看下这些资料`
- 更好的目标：`把这些资料整理成一份 3 页以内的 Markdown 摘要，分成背景、关键发现、待确认问题三部分`

前一句只是启动对话，后一句才真正定义了一个 Agent 任务。

判断目标是否够清楚，可以问自己两个问题：

- 最后要交付什么
- 如果交付完成了，我会怎么知道它完成了

如果这两个问题答不上来，后面所有设计都会漂。

## 2. 输入：限制它“能看什么”，比鼓励它“多看点”更重要

输入是 Agent 最容易被忽略的槽位。很多人下意识会觉得：“模型越强，当然让它看到越多越好。” 但在真实任务里，输入边界比输入数量更重要。

输入至少要回答三件事：

- 它这次读哪些文件、链接或消息
- 它不能读哪些内容
- 输入的格式是否稳定

如果输入边界不清楚，最常见的后果不是“效果差一点”，而是：

- 资料串用
- 读到历史无关内容
- 这次和上次跑出来完全不是同一个任务

所以输入的设计，本质上是 Agent 的第一层安全边界。

## 3. 工具：让它真的能推进事情

没有工具的 Agent，很多时候仍然只是一个会推理的聊天机器人。工具的作用不是“让系统更高级”，而是让它真的能从建议走到动作。

对零基础来说，第一批工具完全不用复杂：

- 读文件
- 写文件
- 搜索
- 一个简单 API

你真正需要先理解的是：

- 哪一步需要它调用工具
- 哪一步不需要
- 工具失败时，任务会卡在哪里

只要这一层明白，后面你再接 MCP 或其他连接器，就不会把“接工具”理解成只是多装一个插件。

## 4. 状态：为什么 Agent 做到一半会断掉

状态这个词听起来抽象，但它在开发里其实很具体。状态回答的是：

- 它现在做到哪一步了
- 上一步产出了什么
- 哪些信息要被带到下一轮
- 这次对话结束后，下次怎么接着做

没有状态设计的 Agent，最常见的问题是：

- 今天做过的事情，下一轮又重新解释一遍
- 中途出错后，不知道从哪里恢复
- 多步骤任务做到一半就断流

所以状态不是“高级功能”，而是复杂任务能不能连续推进的基本条件。

## 5. 输出：没有固定产物，就很难说自己在开发

输出回答的问题是：**这次任务最后到底会落成什么。**

对零基础来说，一个最稳的原则是：优先把输出定义成文件或结构化内容，而不是只停留在聊天区的一段回复。

比如：

- `summary.md`
- `travel-plan.md`
- `todos.json`
- `report.csv`

只要输出固定了，很多事情都会变简单：

- 你知道要验收什么
- 你知道结果落在哪里
- 你知道后续案例怎么复用这个产物

反过来，如果输出是模糊的，“随便给我个建议”这种任务就很难进入工程化。

## 6. 验收：这是把“感觉不错”变成“系统稳定”的关键

验收是这 6 个槽位里最像工程的一个，因为它强迫你回答：

- 什么算通过
- 什么算不通过
- 如果不通过，应该改哪一层

一个没有验收标准的 Agent，会带来一种很危险的错觉：好像每次都“也差不多可以”。但你一旦想复用、想自动化、想给别人用，就会发现完全没法稳定。

验收标准最少应该覆盖：

- 产物是否真的生成了
- 结构是否符合预期
- 关键信息是否完整
- 如果有来源要求，是否可追溯

也就是说，验收决定了你后面能不能把“这次成功”沉淀成模板和工作流。

## 用一个最小例子把 6 个槽位填一遍

假设你想做一个“资料整理 Agent”，把一堆零散资料整理成摘要。那它的 6 个槽位可以长这样：

| 槽位 | 这次怎么填 |
|---|---|
| 目标 | 生成一份 3 段结构的 Markdown 摘要 |
| 输入 | 只读 `input/` 目录下的 5 份资料 |
| 工具 | 读文件、写文件 |
| 状态 | 记录已读文件、当前摘要草稿、待确认问题 |
| 输出 | `output/summary.md` |
| 验收 | 产物存在；结构正确；每段都对应原始资料内容 |

只要你能把一个任务填到这张表里，它基本就已经从“模糊想法”变成“可以开发的 Agent 设计”了。

## 这 6 个槽位是怎么互相影响的

这 6 个槽位不是独立的，它们会互相牵动：

- 目标不清楚，输出就一定模糊
- 输入边界不清楚，状态就容易混乱
- 工具不足，目标就只能降级
- 没有验收，状态再完整也没意义

所以一个 Agent 设计得稳不稳，不在于某一层多高级，而在于这 6 层之间有没有对齐。

## 这一章读完后，你应该能做什么

读完这一章，最重要的不是记住这 6 个词，而是拿一个真实任务，快速判断它是否已经具备开发条件：

- 目标清楚了吗
- 输入边界定了吗
- 工具够不够
- 状态要不要保留
- 输出落在哪
- 验收怎么写

如果这 6 个问题你能逐项答出来，后面你再去学宿主、prompt、工具调用和案例，都会更像是在往同一套骨架里填肉，而不是东学一点西学一点。
