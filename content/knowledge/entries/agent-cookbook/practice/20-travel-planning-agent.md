## 为什么选旅行助手

旅行规划是一个很适合做 Agent 项目的题目，因为它天然就不是单步问答。用户不会只问一句“北京有什么景点”，而是会带着日期、预算、偏好、住宿要求、交通方式一整串条件进来。系统如果只是像聊天机器人那样给一段泛泛建议，基本没法真正用。

更麻烦的是，旅行这件事的信息天生就是散的。景点资料在不同网站上，天气是一套数据，地图路线又是另一套数据，预算还要自己重新算。只要其中一块变了，整个计划都可能要重排。

所以这个项目的价值，不只是“做一个能聊天的旅行顾问”，而是把几件事情接起来：

- 根据输入生成可读的旅行计划
- 把景点、酒店、餐饮、天气、路线放到同一个结果里
- 算预算，而不是只给推荐
- 允许后续编辑，而不是一锤子买卖
- 支持导出，变成真的可带走的结果

## 这个项目最后长什么样

按 `voidagent` 这一章的思路，这个旅行助手最终不是一个命令行 demo，而是一个完整 Web 应用。它至少有几块核心能力：

- 智能行程规划：根据目的地、日期、偏好自动生成旅行安排
- 地图可视化：把景点和路线直接画出来
- 预算计算：门票、交通、酒店、餐饮都要有个大概数
- 行程编辑：删景点、换顺序之后结果能跟着变
- 导出功能：结果能存成图片或 PDF

这几个能力放在一起，才更像一个完整产品。否则很容易只剩“LLM 说了一段看起来不错的话”。

## 架构先怎么理解

这一章里最值得借的，不只是功能清单，还有整体分层方式。可以先按四层去看：

![旅行助手四层架构图](../../assets/agent-cookbook/travel-architecture-stack.svg)

- 前端层：负责表单、结果页、地图展示、编辑交互
- 后端层：负责 API、参数校验、服务编排
- Agent 层：负责拆任务、调工具、整合结果
- 外部服务层：地图、图片、LLM、天气或其他旅行相关服务

这套分层的好处是，项目不会一开始就糊成一团。页面怎么交互是一层，接口怎么组织是一层，Agent 怎么协作是一层，工具怎么接又是一层。后面排错和扩展都会轻松很多。

我这里不准备完全照着原章节顺序抄，而是按更适合“从 0 到 1 跟着做”的方式拆成下面几页：

- 项目概述与架构设计

- 数据模型设计
- 多 Agent 协作设计
- MCP 工具接入

这样顺序更自然。先知道要做什么，再把项目跑起来，再去理解数据、协作、工具和页面，最后回来看细节功能。
