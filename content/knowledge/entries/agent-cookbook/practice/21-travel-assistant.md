## 案例目标

做一个从需求输入到行程输出的智能旅行助手，交付行程、预算、注意事项与来源说明。

## 这一章要讲什么

- 旅行任务如何拆成子问题
- 外部信息源和工具怎么接
- 行程、预算、注意事项怎么一起交付
- 结果怎样做成“真的能用”

## 为什么旅行助手是第二个案例

它非常适合接在对话 Agent 后面，因为它保留了前一个案例里最重要的能力：通过自然语言理解用户需求、补充问题、确认偏好、稳定输出结构。但与此同时，它又往前多走了一步，不再只整理用户已经说出来的内容，而是要处理真实世界里更多条件和约束。

旅行任务的好处是，需求天然是复合型的。目的地、时间、人数、预算、交通、住宿、天气、景点、节奏、饮食偏好，这些东西会同时出现，而且它们之间彼此牵制。也正因为如此，这个案例特别适合用来练“任务拆分”和“信息组装”。

## 这个案例真正要学的不是旅行，而是任务拆分

很多人第一次看到旅行助手，会把注意力放在“能不能做出一个好玩的旅游推荐”。但对 Agent 开发来说，这篇更重要的其实不是旅游内容本身，而是你能不能把一个多条件、多步骤的问题拆成几个稳定的小块。

一个最常见的错误，是把整件事一次性交给 Agent，比如“帮我规划三天去东京的旅行”。这当然能得到一个答案，但你很难判断：

- 哪些条件被真正考虑到了
- 哪些信息是补全的，哪些是猜的
- 预算为什么会变成这个样子
- 某个景点为什么会出现在这一天

所以这篇最核心的训练不是“让结果更花哨”，而是“让生成过程更可解释”。

## 先把用户需求问清楚

做旅行助手时，第一步不是搜景点，而是先把需求问清楚。因为旅行计划一旦缺少基本条件，后面所有看起来很完整的方案都可能只是漂亮的幻觉。

最值得先确认的条件通常包括：

- 目的地和出发地
- 出行日期和天数
- 出行人数
- 预算范围
- 旅行偏好
- 是否有必须去或必须避开的点

这一步本质上仍然是对话 Agent 的能力延续。你会发现，真正好的旅行助手不是一上来就给答案，而是知道什么时候先问问题。

## 旅行任务可以拆成哪几层

如果把这个案例做成一个更像工程对象的系统，通常可以拆成下面几层：

1. 需求收集  
2. 信息检索  
3. 方案组装  
4. 结果交付

这 4 层不是为了显得复杂，而是为了让你知道哪一步在解决什么问题。需求收集解决的是条件不完整；信息检索解决的是材料不足；方案组装解决的是如何在多个约束之间做取舍；结果交付解决的是如何把答案变成用户真正能拿去用的东西。

## 信息检索为什么是这个案例的关键增量

对话 Agent 更多是在整理对话本身，而旅行助手通常会碰到外部信息。哪怕你不真的联网，这个案例也会逼你思考：如果未来接搜索、接 API、接 MCP 工具，哪些信息是必须查的，哪些信息是可以先让用户补的，哪些信息必须带来源说明。

常见会用到的信息包括：

- 往返交通
- 酒店或住宿范围
- 景点开放信息
- 天气情况
- 当地注意事项

也就是说，从这一页开始，Agent 已经不只是“理解用户”，而是开始承担“把外部信息拉进来并组织成答案”的任务。

## 什么信息必须带来源

旅行助手和前面案例最大的不同之一，是结果开始明显依赖外部世界。对话里总结一下想法，偶尔没有来源问题不大；但一旦牵涉交通、预算、时间安排、天气和注意事项，来源就变得很重要。

第一次做这个案例时，不需要把引用系统做得很重，但至少应该让这些高风险信息带上来源说明：

- 价格估算
- 时间安排
- 开放或营业状态
- 天气和季节信息
- 特殊限制或提醒

这样做的意义不是“学术化”，而是让用户知道哪些内容是可核对的，哪些是 Agent 帮忙做的组合和建议。

## 旅行方案不是信息堆砌，而是取舍

很多人做旅行助手时，会自然地走向“尽可能多给一些推荐”。但一个真正可用的旅行计划，不是把所有找到的信息全塞进去，而是根据条件做取舍。

比如：

- 预算有限时，交通和住宿要优先控制
- 带老人或孩子时，行程节奏要更松
- 首次去某城市时，景点密度不宜过高
- 时间很短时，应该减少跨区域移动

这说明旅行助手的核心价值，不只是搜信息，而是把条件之间的冲突真正处理掉。它交付的不是“信息列表”，而是“一个可执行方案”。

## 一个可用的输出结构

为了让这个案例可验收，最好一开始就固定输出结构，而不是想到什么写什么。第一版完全可以先约定成下面这样：

```md
## 旅行概览

### 行程安排

### 预算估算

### 注意事项

### 关键来源说明
```

这套结构的好处是，你可以很容易检查它有没有真的把任务完成。有没有行程，有没有预算，有没有注意事项，有没有来源，一眼就能看出来。

## 一个最小 Prompt 示例

把这个案例压成可运行的最小版本，可以写成下面这样：

```md
你是一个“智能旅行助手”。

你的职责：
- 根据用户的出行需求整理旅行条件
- 如果条件不足，先提问补齐
- 基于已知信息输出行程、预算和注意事项
- 对关键信息给出来源说明

你的边界：
- 不编造具体价格、时间和开放信息
- 如果外部信息不足，明确标出“待确认”
- 不为了让行程看起来丰富而强行塞入过多安排

输出结构固定为：
1. 旅行概览
2. 行程安排
3. 预算估算
4. 注意事项
5. 关键来源说明
```

到这里，这个案例已经不是“帮我推荐去哪玩”，而是一个带任务结构、带条件收集和带来源意识的真实世界 Agent。

## 一个最小输入例子

例如用户这样说：

```md
我想和朋友 10 月去东京玩 4 天，预算每人 6000 元左右，想吃好一点，但不想把每天排得太满。我们第一次去东京。
```

面对这样的输入，一个成熟一点的旅行助手不该立刻输出完整答案，而是先判断哪些条件已经足够，哪些地方还缺。例如，它可能先补问：

- 出发地是哪里
- 预算是否包含机票和酒店
- 更偏好市区还是近郊
- 有没有必须去的点

你会发现，这一步仍然是“需求澄清”，只是它已经开始为后面的真实方案做准备。

## 这个案例怎么验收

这篇最重要的不是做出一个特别长的旅行攻略，而是确认它能不能稳定地产出一个“真的能拿来参考”的计划。最直接的验收方式可以是：

1. 条件不足时，它是否先提问  
2. 最终结果里是否同时包含行程、预算、注意事项和来源说明  
3. 预算和节奏是否与用户偏好一致  
4. 不确定的信息是否被清楚标记，而不是被硬填满

这几条检查下来，你就能很快分辨它到底是“很会写旅行文案”，还是“真的会组织旅行任务”。

## 一组最小测试输入

你可以用下面两组输入来测试这个案例。

第一组，用来测条件补齐：

```md
用户：
帮我规划一下去大阪玩几天的行程。

期待表现：
- 不直接硬写完整攻略
- 先追问日期、预算、人数和偏好
```

第二组，用来测结果交付：

```md
用户：
我和对象 12 月去上海玩 3 天，预算一共 5000 元左右，想轻松一点，喜欢散步和吃东西。

期待输出：
- 一份 3 天行程
- 预算估算
- 注意事项
- 来源说明或待确认项
```

只要这两组能稳住，这个案例就已经成立了。

## 最常见的坑

第一次做旅行助手，最常见的问题通常有 5 个：

- 条件还没问清就急着给完整方案
- 把推荐写得很热闹，但没有预算逻辑
- 结果只有行程，没有注意事项
- 所有外部信息都写得很肯定，却没有来源
- 输出像一篇长文，而不是一个好用的计划

这些问题的共同点是：它们让内容看上去丰富，却不够可靠。对真实世界任务来说，可靠通常比热闹更重要。

## 为什么这个案例是通往多 Agent 的桥

旅行助手虽然现在还可以先按单 Agent 来写，但它已经天然带出多角色拆分的思路。你会很容易发现，有些部分更像“需求澄清助手”，有些部分更像“信息检索助手”，还有些部分更像“行程组装助手”。

这正是它适合作为第二个案例的原因。它让你第一次看到：一个真实任务为什么会自然地逼出多个子模块，甚至将来逼出多个 Agent。也就是说，这篇其实是在为最后的多 Agent 系统做桥接。

## 这一章读完后，你应该能做到什么

读完这一章后，你至少应该能把一个旅行任务拆成几个清楚的子问题，知道哪些信息要先问、哪些信息需要来源、哪些内容要放进最终交付里。更重要的是，你应该能看出一个“旅行推荐”什么时候只是会写文案，什么时候已经开始像一个能组织现实任务的 Agent。

只要这一层建立起来，最后去做多 Agent 系统时，你就不会只是在堆角色，而会知道每个角色到底在解决哪一段真实问题。
