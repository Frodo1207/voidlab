## 为什么这一页很重要

旅行助手不是只传一段文本来回。前端表单会交一批字段，后端会转成内部对象，Agent 会再调用地图、图片、酒店、天气这些外部服务，最后结果还要重新回到前端页面里展示。

这中间如果没有一套统一数据结构，项目很快就会乱：有的接口叫 `lng`，有的叫 `longitude`；有的价格是数字，有的是字符串；有的结果有图片，有的只有描述。后面页面越做越多，问题只会越来越难排。

`voidagent` 这一章专门把“从字典到 Pydantic 模型”讲得很细，核心意思就是：这类 Web + Agent 项目，一定要尽早把数据模型定下来。

## 先从最底层开始

一个比较顺的做法不是先写“总行程对象”，而是先把最基础的东西拆出来：

![旅行助手数据模型关系图](../../assets/agent-cookbook/travel-data-model-map.svg)

- `Location`：经纬度
- `Attraction`：景点
- `Hotel`：酒店
- `Meal`：餐饮
- `Budget`：预算

这些模型先稳定，后面再去组合 `DayPlan`、`TripPlan` 这类更大的结构。这样每一层都更容易检查，也更容易给前端和后端共享理解。

## 为什么推荐 Pydantic

如果后端是 Python，这里用 Pydantic 很顺。原因不是“它高级”，而是它正好解决了这类项目最头疼的几件事：

- 字段校验
- 类型转换
- 默认值处理
- 嵌套对象表达
- 和接口输入输出对齐

比如天气接口回来的温度可能是字符串，地图接口回来的经纬度格式也不统一，这种地方如果每次都手动处理，很容易满地都是小坑。模型层先做一次收口，后面就干净很多。

## 这一页真正要产出的东西

到这一步，课程里最该落下来的，不是完整数据库，而是一套项目里的公共对象定义。最少要能回答这几个问题：

- 一个景点对象里到底有哪些字段
- 一个酒店对象里有哪些字段
- 一天的行程怎么表示
- 整个旅行计划怎么表示
- 预算和天气是挂在哪一层

这一步做稳了，后面的多 Agent 协作、前端结果页、预算汇总、导出功能都会轻松很多。
