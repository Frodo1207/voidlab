## 为什么这里开始要拆角色

旅行规划看起来像一件事，实际拆开是好几件事：找景点、查路线、看天气、补酒店、算预算、最后再整理成一个能读的计划。如果都塞给一个 Agent，理论上不是不能做，但提示词会越来越长，出错以后也很难定位。

`voidagent` 这一章专门把这块拆成多 Agent 协作设计，核心思路很简单：让不同角色负责不同子任务。

## 可以怎么拆

这一类项目，比较顺手的拆法通常是：

![旅行助手多 Agent 协作主线](../../assets/agent-cookbook/travel-multi-agent-flow.svg)

- 行程规划 Agent：负责把用户需求变成整体日程
- 景点 Agent：负责找候选景点和基础资料
- 酒店 / 餐饮 Agent：负责补住宿和用餐建议
- 汇总 Agent：负责把分散结果收成统一输出

也不一定非要 exactly 按这个名字来，重点是不要让一个 Agent 又查资料、又排顺序、又算预算、又管输出格式。

## 多 Agent 的好处在哪

角色拆开之后，最直接的好处有三个：

- 提示词更短，更容易调
- 哪一块出错更容易定位
- 某个子能力以后可以单独替换或增强

比如“找景点”这块效果不好，不需要把整个系统推翻重做，只要盯着那一个角色改就行。

## 协作顺序怎么想

这类项目最顺的协作链路一般不是并行乱飞，而是有一个主线：

1. 先拿到用户约束
2. 再补信息和候选方案
3. 再做规划与取舍
4. 最后统一汇总输出

也就是说，多 Agent 不是为了显得高级，而是为了让任务拆得更自然。旅行规划本来就是一个要不断补信息、不断判断的过程，用多个角色来承接这件事，本来就更符合问题结构。
