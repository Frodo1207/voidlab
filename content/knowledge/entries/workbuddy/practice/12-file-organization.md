## 一句话结论

文件整理的交付物不是“干净”，而是三样东西：**统一命名、统一目录、统一索引**。只要这三样落地，你下个月还能用同一套规则继续整理，而不是又回到桌面堆满的状态。

## 适用对象

- 你经常在 `桌面 / 下载 / 微信文件 / 飞书下载 / 浏览器下载` 里找不到东西
- 你需要把资料整理给团队或客户，但又怕遗漏、怕重复、怕串用
- 你希望 WorkBuddy 真的“动手整理文件”，而不是只给建议

## 前置条件

- 先选定一个明确工作区目录（建议新建 `FileOrg/` 或项目目录），不要直接在全盘资料库上跑任务
- 第一次建议用默认权限，避免误删误移；要提速也得等跑通 2~3 次后再开完全访问
- 建议先做一次快照备份：把整理目标目录压缩成 `backup.zip`，或者复制到 `backup/`（不用很优雅，但必须能回滚）

WorkBuddy 在“任务 + 工作区”的逻辑里，本质就是把它能读写的文件集合收进一个边界内，这也是做文件整理时最重要的安全带。[$TRAE_REF](https://workbuddy.homes/bluebook/%E7%AC%AC%E4%B8%80%E7%AF%87%20%E4%BD%BF%E7%94%A8%E6%89%8B%E5%86%8C%EF%BC%9A%E5%85%88%E6%8A%8A%20WorkBuddy%20%E7%94%A8%E8%B5%B7%E6%9D%A5/%E7%AC%AC%203%20%E7%AB%A0%20WorkBuddy%20%E7%9A%84%E4%B8%BB%E7%95%8C%E9%9D%A2%E3%80%81%E4%BB%BB%E5%8A%A1%E4%B8%8E%E5%B7%A5%E4%BD%9C%E5%8C%BA/)

## 最短路径（可验收）

你第一次做，不要追求一步到位。最短可验收路径是：**把散落文件收进一个“收件箱目录” → 统一命名 → 按规则落盘到归档目录 → 输出一份清单**。

完成后你应该拿到 4 个交付物：

- `archive/`：分类后的目录结构（可持续增长）
- `rules/naming.md`：命名规则（写清楚，后面才能复用）
- `output/manifest.csv`：文件清单（可检索、可审计、可交接）
- `output/changes.md`：变更说明（这次移动/重命名了什么）

## 关键步骤拆解

### 步骤 0：把“整理范围”写死

文件整理最怕两件事：

- 范围无限扩大：从桌面整理到“顺手把整个硬盘也整理了”
- 规则临场发明：整理到一半改命名法，最后所有文件都像不同人整理的

所以第一步不是动文件，是先写清楚三件事：

| 项目 | 你要写清楚什么 | 例子 |
|---|---|---|
| 范围 | 只整理哪些目录 | 只整理 `Desktop/ToSort` 与 `Downloads/ToSort` |
| 时间 | 是否只整理某段时间 | 只整理近 90 天 |
| 目标 | 归档到哪里 | 全部落到 `FileOrg/archive/` |

### 步骤 1：先做“收件箱”与去重

把所有散落文件先复制或移动到一个地方（建议先复制，跑通后再改为移动）：

```txt
FileOrg/
  inbox/          # 原始收件箱（第一次建议只进不出，避免误删）
  archive/        # 归档目录
  rules/          # 命名与归档规则
  output/         # 清单与日志
```

去重建议先用“弱规则”，不要一上来做内容级哈希（第一次会把复杂度拉爆）：

- 同名文件保留最新修改时间的版本
- 对 `xxx(1).pdf`、`xxx-副本.pdf`、`xxx copy.pdf` 做统一归并
- 图片类先按“拍摄时间/创建时间 + 分辨率”粗去重，无法判断的写入“待人工确认清单”

### 步骤 2：统一命名（这一步决定你以后能不能找回）

一个可长期复用的命名规则，必须满足两点：

- 机器可排序：按文件名就能大致按时间/项目排序
- 人可扫读：看到名字就知道是什么，不用打开

推荐命名法（够用、易坚持）：

```txt
YYYYMMDD__project__topic__v01.ext
```

规则说明：

- `YYYYMMDD` 用“文件所属事件日期”，不要用“整理当天日期”
- `project` 是你能稳定复用的主分类（客户名/产品名/部门名/主题名）
- `topic` 用短语描述内容（不超过 12 个汉字或 24 个英文字符）
- `v01` 只在你确实会迭代的文档上使用（方案、合同、报价、简报）

常见扩展字段（按需加，不要全加）：

- `__src-wechat`、`__src-feishu`：来源标记
- `__confidential`：敏感标记（也可以用目录权限隔离）

### 步骤 3：归档目录设计（尽量少层级）

目录层级越深越难坚持，越容易“归档完就再也找不到”。一个稳的归档结构通常不超过两层：

```txt
archive/
  10-clients/
    client-a/
    client-b/
  20-products/
    product-x/
  30-admin/
    finance/
    legal/
  90-scratch/
```

建议你把目录当作“长期口径”，把更细的分类交给 `manifest.csv`（索引清单）去解决。

### 步骤 4：输出清单（manifest）让它可检索、可交接

不管你整理得多漂亮，只要没有清单，这件事就没法验收，也没法交接给别人。

推荐输出 `output/manifest.csv` 至少包含这些列：

| 列 | 含义 |
|---|---|
| path | 归档后的相对路径 |
| filename | 文件名 |
| type | 文件类型（pdf/docx/xlsx/png/other） |
| project | 项目/客户/主题 |
| date | 事件日期（从文件名解析） |
| source | 来源（可选） |
| notes | 备注（可选） |

同时输出 `output/changes.md`，把本次整理的行为记录下来：

- 新增了哪些目录
- 重命名了哪些文件（旧名 → 新名）
- 无法自动分类的文件列表（需要你确认）

### 步骤 5：验收（通过/不通过）

文件整理的验收不是“看起来很整齐”，而是能不能满足下面这些可检查条件：

- 归档目录 `archive/` 内不存在 `未命名`、`新建文件夹`、`final_final` 这类不可维护命名
- 任意抽查 10 个文件：只看文件名就能说出它是什么、属于哪个项目、什么时候发生
- `manifest.csv` 中的文件数与 `archive/` 实际文件数一致（允许少量“待人工确认”例外，但必须列出来）
- `changes.md` 能回放这次整理做了什么（便于回滚和复盘）

## 可复用模板

下面这段可以直接复制到 WorkBuddy 作为任务说明。它遵循“目标/输入/动作/约束/输出/验收”六要素，这也是官方在第 4 章强调的可验收任务写法。[$TRAE_REF](https://workbuddy.homes/bluebook/%E7%AC%AC%E4%B8%80%E7%AF%87%20%E4%BD%BF%E7%94%A8%E6%89%8B%E5%86%8C%EF%BC%9A%E5%85%88%E6%8A%8A%20WorkBuddy%20%E7%94%A8%E8%B5%B7%E6%9D%A5/%E7%AC%AC%204%20%E7%AB%A0%20%E5%BF%AB%E9%80%9F%E5%AE%8C%E6%88%90%E7%AC%AC%E4%B8%80%E4%B8%AA%20WorkBuddy%20%E4%BB%BB%E5%8A%A1/)

```txt
目标：把指定范围内的散落文件整理成“可检索、可归档、可持续维护”的结构，并输出可验收的清单与变更说明。

输入：
- 整理范围：{写清楚目录或文件夹}
- 只处理：{例如近 90 天；或全部}

动作：
1) 将范围内文件汇总到 inbox/（第一次建议复制，不直接移动）
2) 去重：合并 copy/副本/重复下载
3) 统一命名：YYYYMMDD__project__topic__v01.ext
4) 归档到 archive/：按 10-clients/20-products/30-admin/90-scratch 结构落盘
5) 输出 manifest.csv 和 changes.md

约束：
- 不删除任何文件；无法判断的放入 output/pending-review/ 并在 changes.md 列出
- 不改写原始文件内容，只做复制/移动/重命名
- 命名规则一旦确定，本次任务内不允许临时修改

输出：
- archive/（归档结构）
- rules/naming.md（命名规则说明）
- output/manifest.csv（文件清单）
- output/changes.md（变更日志）

验收：
- manifest.csv 文件数与 archive/ 实际文件数一致（待人工确认的必须单列）
- 任意抽查 10 个文件，文件名可读且含日期与项目
- changes.md 能回放本次做过的重命名与归档动作

开始前先给我：你拟定的目录结构草案 + 命名规则示例 10 条，我确认后再执行实际整理。
```

## 常见坑与排查

- 规则写得太复杂：先用 `YYYYMMDD__project__topic`，跑通再加版本号/来源标记
- 一上来就移动原件：第一次建议复制到 `inbox/`，确认结果再做“移动版”
- 只整理目录不输出清单：没有 `manifest.csv` 就无法验收，也无法交接
- 把“分类”当成目的：分类只是手段，目的是以后能找回、能复用、能审计
