自动化最常见的误解是：能跑一次，就算自动化成功。实际上，一次跑通只证明“这个流程存在”，并不证明“它可靠”。真正的可靠性，是它在你不盯着的时候，依然能稳定地产出同样结构的结果，并在失败时给你足够明确的回退路径。

这篇不是讲“怎么定时运行”，而是讲：**什么样的任务才配自动化、自动化之后怎么避免静悄悄地坏掉**。

## 一句话结论

自动化的核心不是“无人值守”，而是**可重复、可观测、可回退**。只要缺一个，它就不是资产，而是定时制造麻烦的脚本。

## 可靠性要看什么

- 是否会因为休眠中断
- 是否能重复跑出同样结构
- 失败时是否有回退

我建议把“可靠性”固定拆成 5 个检查维度：

| 维度 | 要回答的问题 |
|---|---|
| 输入稳定性 | 每次拿到的是不是同一类输入、同一口径 |
| 输出稳定性 | 每次输出结构是否一致、落点是否固定 |
| 可观测性 | 你能不能看见它跑了什么、哪里错了 |
| 失败回退 | 失败后能不能快速恢复、不扩大损失 |
| 幂等性 | 重跑一次会不会重复创建、重复发送、重复写入 |

## 自动化前必须先有

- 稳定的输入
- 稳定的输出
- 可检查的验收标准

这三项其实就是自动化的最低门槛。更具体一点：

- 输入不稳定：今天是链接，明天是截图，后天是口头转述，这种流程不能直接自动化
- 输出不稳定：今天生成文档，明天生成表格，文件名和目录每次都变，这种流程不能自动化
- 验收不稳定：你自己都说不清“什么算成功”，这种流程只能继续半自动

## 什么任务适合先自动化

最适合率先自动化的任务有两个特征：

- 高频重复：每天/每周都会发生
- 结构稳定：输入形态和输出形态基本不变

典型例子：

- 每日资讯摘要
- 会议纪要整理后的固定同步
- 邮件线索整理
- 周报汇总

不适合直接自动化的任务：

- 一次性策略分析
- 需要强判断、强创意、强人工确认的高风险任务
- 涉及不可逆写操作但还没稳定过的流程

## 自动化的四段可靠性设计

### 1) 输入层：先把入口固定

输入层最怕“悄悄变化”。所以自动化的第一层不是调度，而是输入契约：

- 输入来自哪里：某个目录、某个标签、某个表、某个时间窗口
- 输入长什么样：字段、文件格式、命名规则、必填项
- 缺输入怎么办：跳过、报错、还是生成空报告

经验规则：**任何自动化任务，先把输入写成一个人类也能检查的说明文件**。

### 2) 处理层：输出必须可预测

处理层要解决的是“每次跑出来的东西是不是同一种东西”。

你至少要固定：

- 输出目录
- 文件命名规则
- 文档/表格/消息的固定结构
- 成功后的变更清单

如果输出形态不稳定，你后续就没法接自动验收，也没法接团队协作。

### 3) 观测层：不要让失败静默发生

自动化最危险的是“看起来正常，但其实已经坏了 3 天”。所以可观测性至少要做到：

- 每次运行有记录（开始时间、结束时间、是否成功）
- 成功时知道产物在哪里
- 失败时知道卡在哪一层（输入/权限/连接器/格式/写入）

最低配也应该有：

- `run_log.md` 或运行日志
- `change_log.md` 或变更清单
- 失败摘要（不是一堆堆栈，而是人能读懂的原因）

### 4) 回退层：任何写操作都要能降级

一条很实用的原则：**自动化只要涉及外部写操作，就必须先设计手动 fallback**。

例如：

- 发消息失败：先把内容保存到 `output/draft.md`
- 写表失败：先导出 `output/report.csv`
- 创建文档失败：先生成本地 `output/report.md`

这意味着即使自动化失败，任务也不会完全丢失。

## 幂等性：重跑不会制造第二次事故

自动化真正的“工程味”在这里。幂等性的问题是：

- 同一封邮件会不会被重复整理两次
- 同一条消息会不会被重复发送两次
- 同一份日报会不会重复覆盖或重复发布

最简单的处理方式：

- 给每次运行一个 `run_id`
- 给每份产物一个“日期 + 任务名”的唯一键
- 写入前先检查“今天这份是否已经存在”

如果不能幂等，自动化就会在重试时制造新问题。

### 模板 B：WorkBuddy 任务说明（自动化前的稳定性检查）

这段不是直接让它“自动跑”，而是先让它审计一个任务是否适合自动化。这样比一上来定时执行稳很多。

```txt
目标：审计当前工作流是否已经达到“可自动化”的最低标准，并输出自动化设计卡与风险清单。

输入：
- 现有流程说明
- 当前输入样例
- 当前输出样例

动作：
1) 检查输入是否稳定（来源/格式/字段/命名是否固定）
2) 检查输出是否稳定（目录/文件名/结构/验收是否固定）
3) 检查是否存在外部写操作，并给出失败回退方案
4) 检查是否具备幂等性（重跑不会重复创建/发送/写入）
5) 生成自动化设计卡 + 风险清单

输出：
- output/automation-design-card.md
- output/automation-risks.md

验收：
- 我能根据 design card 判断这个流程能不能上自动化
- 每一个高风险点都对应一个 fallback 方案
```

### 模板 C：自动化运行日志（run_log.md）

```md
# run log

- run_id:
- status: success / failed / partial
- input_range:
- outputs:
- errors:
- fallback_used:
```

## 常见坑与排查

- 能跑一次就上自动化：先连续人工跑通 3 次，再考虑调度
- 输出文件名每次不同：固定命名规则，不然无法接下游
- 错了也不报警：至少要有失败摘要和运行日志
- 外部写操作没有草稿回退：一旦失败就全损；必须先落本地草稿
- 重试直接再跑一遍：先解决幂等性，否则会重复发送/重复创建
