## 一句话结论

好的 Agent 提示词不是“更会说”，而是更像任务契约。

## 这一章要讲什么

- 为什么要写清楚输入与边界
- 输出与验收怎么写
- 常见坏提示词长什么样
- 为什么零基础最容易忽略“约束”和“验收”

## 为什么 Prompt 会被写坏

很多人第一次写 Agent 提示词，会不自觉回到聊天习惯：给一个大致想法，剩下的交给模型自己理解。这样在普通问答里偶尔还能成立，但一旦任务要接文件、接工具、接外部动作，这种写法几乎一定会出问题。因为 Agent 不只是“回答你”，它还会真的去读、去写、去改、去生成产物。

于是最常见的坏结果不是“它太笨”，而是任务本身没有被定义清楚。它可能很努力地做了很多事，但方向偏了；也可能产出了看起来像结果的内容，但你根本不知道该不该通过。这时候问题不在文采，而在契约没有立起来。

## Prompt 到底在契约什么

在 Agent 开发里，`Prompt` 的作用不是让模型“更有灵性”，而是定义这次运行该怎么发生。上一章我们把宿主里的中间对话区看作任务定义区，这一章就是把那块区域真正写实：你说的每一句话，最好都能落到一份任务契约的组成部分上。

一份最小可用的契约，至少要回答 5 个问题：

- 目标：这次到底要完成什么
- 输入：它允许看什么材料
- 约束：它应该遵守什么边界
- 输出：最后要交付什么
- 验收：做到什么程度才算通过

如果这 5 件事里缺了两三件，任务通常还能“跑”，但很难稳定。第一次也许碰巧成功，第二次就会漂；换一批资料、换一个宿主、换一个模型，结果就不一样了。

## 5 段式任务契约

### 目标

目标不是写一个大而空的愿望句，而是告诉 Agent，这次运行结束时世界应该变成什么样。比如“帮我整理资料”就太虚，“把 `input/interview.md` 整理成一份 800 字以内的面试摘要，写入 `output/brief.md`”就清楚得多。

好的目标会让 Agent 知道自己为什么工作，也知道什么时候应该停。没有这个终点，它很容易在“再补充一点内容”和“已经够了”之间来回摇摆。

### 输入

输入是在划边界。你要让 Agent 知道，它这次应该看哪些文件、哪些网页、哪些用户消息、哪些数据源，而不是默认“能看到的都算材料”。

零基础最容易忽略这一点，是因为聊天时我们习惯靠上下文补全。但 Agent 一旦进入工作区，输入边界不清楚，常见后果就是串料、误读旧文件、引用错版本，最后连你自己都说不清它是基于什么做出的结果。

### 约束

约束决定的是手感和风险。这里写的不是重复目标，而是告诉 Agent 哪些事不能做、哪些偏好必须遵守、哪些方式优先。

常见约束包括：

- 不要编造不存在的信息
- 只使用当前工作区提供的材料
- 如果信息不足，先标出缺口，不要自行补齐
- 输出使用中文
- 不修改原文件，只生成新文件

很多人把 Prompt 写坏，不是目标不清楚，而是没有约束。没有约束的 Agent 往往显得很主动，但越主动越容易越界。

### 输出

输出决定交付物的形状。它最好回答这些问题：产物是什么类型，写到哪里，用什么结构，长度大概多少，是否需要分段、表格、标题、来源说明。

如果你只写“给我一个结果”，Agent 往往会把聊天回复本身当成结果。但在开发任务里，真正有价值的往往不是聊天框里的几段话，而是一个文件、一份结构化内容、一段可复用代码、一个明确的产物路径。

### 验收

验收是最容易被省略的一段，但它决定了这次任务到底能不能进入“工程状态”。因为没有验收，你只能凭感觉判断结果；有了验收，你才知道这次运行该不该通过，下一轮返工该改哪一块。

验收不一定很复杂，但一定要能检查。比如：

- 文件真实生成在指定路径
- 摘要不超过 800 字
- 必须包含 3 个核心观点和 1 个风险提醒
- 不能出现材料中没有的信息

只要验收写得足够具体，Prompt 就不再只是“指令”，而是一个可以复盘的任务定义。

## 一个坏提示词怎么改成契约

下面这个例子很典型：

> 帮我整理一下这份采访内容，输出一版摘要，写得专业一点。

这句话不是完全不能用，但它没有解决最关键的几件事：材料在哪，摘要写到哪，多少字算合适，专业一点具体是什么意思，怎么判断做得对不对。结果就是 Agent 只能猜。

可以把它改成下面这样：

```md
请读取 `input/interview.md`，整理成一份面向产品团队的采访摘要，写入 `output/interview-brief.md`。

要求如下：
- 使用中文
- 全文控制在 800 字以内
- 结构固定为：背景、3 个核心发现、1 个风险提醒、结论
- 不要编造材料中没有的信息
- 如果材料不足以支持某个结论，直接标出“信息不足”

验收标准：
- 文件成功写入 `output/interview-brief.md`
- 摘要包含 3 个核心发现和 1 个风险提醒
- 没有出现原材料里不存在的新事实
```

这时你会发现，Prompt 的质量提升，并不是因为句子变华丽了，而是因为它把“目标、输入、约束、输出、验收”补齐了。

## 坏提示词通常坏在哪里

| 常见写法 | 真正缺的东西 | 典型后果 |
|---|---|---|
| “帮我整理一下” | 目标、输出 | 做成摘要、表格还是清单，全靠猜 |
| “按你的理解来” | 约束、验收 | 很主动，但风格和边界漂移很大 |
| “参考这些资料写一版” | 输入边界 | 旧资料、错版本、无关材料容易混进来 |
| “写得专业一点” | 可检查标准 | 你和 Agent 对“专业”的理解完全不同 |
| “先做做看” | 输出路径、通过条件 | 聊天框看起来完成了，文件却没有落盘 |

这些问题有一个共同点：它们都把关键判断留在运行过程中临时决定。对聊天来说这不算致命，但对 Agent 开发来说，这会让结果很难复现。

## 零基础最该先练的不是文风，而是定规格

很多人会花很长时间琢磨“要不要更礼貌一点”“要不要加角色设定”“要不要写得更像高手在说话”。这些当然偶尔有用，但对零基础起步阶段，决定成败的通常不是修辞，而是规格。

真正应该先练熟的是：

- 产物路径能不能写清楚
- 输入边界能不能写清楚
- 约束条件能不能写清楚
- 验收标准能不能写清楚

只要这几件事清楚，语言就算朴素，Agent 也更容易稳定。反过来，如果这些都没写清楚，再华丽的 Prompt 也很难撑住真实任务。

## 一份可以直接复用的任务模板

你可以先把下面这份模板当成默认起手式：

```md
任务目标：
请完成什么任务，最终产物是什么。

输入材料：
这次只允许使用哪些文件、网页、消息或数据。

约束条件：
- 使用什么语言
- 不允许做什么
- 信息不足时怎么处理
- 是否允许修改原文件

输出要求：
- 产物文件路径
- 固定结构或字段
- 长度或格式要求

验收标准：
- 怎么确认文件已经生成
- 内容必须包含什么
- 内容不能出现什么
```

这份模板的价值，不是让你以后机械套表格，而是帮你养成一种判断习惯：每接到一个模糊想法，都先问自己，这 5 段有没有补齐。

## 宿主里的对话区应该怎么用

如果你现在回头看上一章，会发现宿主里的对话区并不神秘。它最重要的用途，就是承载这份契约。你不是在里面“想起什么说什么”，而是在逐步把任务定义清楚。

所以一次好的交互通常会长这样：

1. 先给出第一版契约
2. 看 Agent 是否正确理解输入和产物
3. 如果结果不对，优先补约束和验收，而不是只说“再改一下”

这也是为什么返工时最有效的句子，往往不是“重写”，而是“保持输入不变，把输出结构改成三段，并补充风险提醒”。你改的是契约，不是情绪。

## 写 Prompt 时最值得先检查的 4 件事

第一次上手时，不需要把 Prompt 写得很长。只要在提交前快速看 4 件事：

1. 它最后会不会生成一个明确产物
2. 这个产物有没有指定路径或结构
3. 它是否清楚限定了输入边界
4. 我能不能一句话说出通过条件

如果这 4 件事里有两件答不上来，先别急着运行。多写两行契约，通常比多跑两次返工更省力。

## 这一章读完后，你应该能做到什么

读完这一章后，你不需要成为“提示词高手”，但你至少应该能做到三件事：看出一个 Prompt 是在聊天还是在定义任务；把一个模糊想法改写成 5 段式契约；在结果不稳定时，知道优先补目标、边界、约束还是验收。

只要这一步完成，后面学工具调用和第一个可交付 Agent 就会顺很多。因为从这一章开始，Prompt 不再是玄学，而是工程接口。
