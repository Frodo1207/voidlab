## 一句话结论

第一个 Agent 的目标不是炫技，而是跑通一个最小可交付闭环。

## 这一章要讲什么

- 选一个什么样的任务作为第一个 Agent
- 怎样定义产物与验收
- 怎样保留变更与追溯
- 如何让“第一次成功”成为后面案例的基础

## 为什么第一篇一定要讲“可验收”

很多人做第一个 Agent 时，最容易追求的是“看起来聪明”。它能不能说得像回事，能不能多做几步，能不能显得自动化程度很高，常常会先吸引注意力。但真正决定这个 Agent 是否站得住的，通常不是这些，而是另一件更朴素的事：你能不能检查它这次到底做成了没有。

这也是为什么前面几章要先讲骨架、宿主、Prompt 契约和工具调用。因为如果没有输入边界、没有动作路径、没有产物落点，你最后只能说“感觉还行”。而“感觉还行”不能复用，也不能排错，更不能作为后面案例的起点。

## 第一个 Agent 应该选什么任务

第一次任务的选择，几乎会决定你对 Agent 开发的第一印象。如果你一开始就选那种输入很多、工具很多、结果格式很多、外部依赖很多的任务，第一次失败的概率会很高，而且很难知道到底哪里错了。

所以第一个 Agent 最适合的任务，通常有 4 个特点：

- 输入已知，而且数量不多
- 工具动作单一，最好就是读和写
- 输出形状明确，不需要你临场判断
- 验收方式肉眼可见，不需要复杂打分

换句话说，第一个任务不要追求“大”，要追求“能看懂整条链路”。只要这条链路第一次跑通，后面加复杂度才有意义。

## 一个最合适的首个任务长什么样

最稳的一类首个任务，往往是“读取一份材料，整理成一份新产物”。例如：

- 读取会议纪要，生成结构化摘要
- 读取一篇采访稿，生成采访简报
- 读取零散笔记，生成整理后的清单

这类任务的好处是，它既足够真实，又不会把你拖进太多外部变量里。你能看见输入，也能看见输出，还能很直观地判断内容是否越界、结构是否合格。

## 为什么“可交付”比“会多步推理”更重要

第一次成功最重要的不是模型在内部做了多少推理，而是最后有没有留下一个你能接住的东西。对开发任务来说，这个“能接住的东西”通常就是文件产物和运行痕迹。

只要有了这两个东西，你就拥有了三个关键能力：

- 能检查结果是不是达标
- 能复盘这次到底做了什么
- 能在下一轮只修改一小段，而不是从头再来

这也是为什么“可交付”是第一个 Agent 的核心词。它决定了你的系统是一次性表演，还是一个可以继续长大的工程对象。

## 第一个 Agent 最小闭环应该包含什么

到了这一页，前面几章其实已经能拼起来了。一个最小可验收 Agent，至少应该包含下面几块：

1. 一个明确输入  
2. 一份任务契约  
3. 一次可见的工具动作  
4. 一个真实落盘的产物  
5. 一份能回头检查的运行记录

前四项解决“它有没有做事”，最后一项解决“这次做事能不能复盘”。如果只做到前四项，它还只是一次成功；加上运行记录，它才开始像一个稳定系统。

## 产物要怎么定义才算清楚

“输出一版结果”这种写法还是太松。一个真正可验收的产物，最好至少写清楚下面这些东西：

- 文件路径
- 文件类型
- 固定结构
- 长度或字段限制
- 是否允许新增推断

比如“生成摘要”就不够清楚，但“把 `input/raw-notes.md` 整理成 `output/meeting-brief.md`，结构为背景、3 个重点、1 个待确认问题，总长不超过 800 字”就已经足够清楚。到这一步，产物不再是模糊愿望，而是一个可以被检查的对象。

## 验收标准为什么一定要写在前面

很多人习惯先让 Agent 跑，再凭结果倒推标准。但在 Agent 开发里，更稳的做法恰好相反：先写验收，再运行。因为验收标准会反过来逼你把任务定义清楚。

例如，如果你写不出“通过条件”，往往说明这些地方至少有一处还没想明白：

- 产物到底长什么样
- 输入边界到底在哪
- 它能不能新增材料里没有的内容
- 失败时到底算部分成功还是直接失败

所以验收标准不是结束语，而是任务定义的一部分。写得越早，返工越少。

## provenance 为什么重要

`provenance` 这个词可以简单理解成“这次运行留下的来路说明”。它不一定非要很复杂，也不一定非得是正式日志文件，但至少要让你能回答这些问题：

- 这次读了哪些输入
- 这次写了哪些文件
- 有没有跳过某些内容
- 有没有失败或回退

只要这些问题能回答，你以后再看这次运行，就不会只剩一个孤零零的结果文件。你会知道结果是怎么来的，也会知道下次哪里可以改得更稳。

## 最小 provenance 可以长什么样

第一次不需要把日志系统做得很重。一个最小版本，完全可以只是 `output/provenance.md` 里的一段简单记录：

```md
# provenance

- 输入：`input/raw-notes.md`
- 输出：`output/meeting-brief.md`
- 动作：读取原始笔记，整理为结构化摘要
- 约束：只使用本地材料，不新增外部事实
- 结果：已完成
- 备注：有 1 处信息不足，已在摘要中标出
```

这份东西的价值不在于形式，而在于它让“这次运行发生了什么”第一次被留下来。后面当你进入案例和多 Agent 系统时，这种记录会越来越重要。

## 一个最小可验收 Agent 示例

如果把前面几章压成一个最小例子，它可以长这样：

```md
请读取 `input/raw-notes.md`，整理成一份会议摘要，写入 `output/meeting-brief.md`，并同时生成 `output/provenance.md` 记录本次运行。

要求如下：
- 只使用 `input/raw-notes.md`
- 使用中文
- 摘要结构固定为：背景、3 个重点、1 个待确认问题
- 不修改原文件
- 如果原材料不足，直接标注“信息不足”

验收标准：
- 成功生成 `output/meeting-brief.md`
- 成功生成 `output/provenance.md`
- 摘要包含 3 个重点和 1 个待确认问题
- 不出现原材料中没有的新事实
```

到这里，这个 Agent 已经不是一句模糊指令，而是一个真正有输入、有动作、有产物、有记录、有验收的最小系统。

## 第一次成功后，最该复盘什么

很多人第一次跑通之后，会立刻想加更多能力：联网、更多工具、更复杂结构、更长上下文。其实更值得先做的，是先复盘一次最小闭环。你至少要回头看清楚这几件事：

1. 输入是不是控得住  
2. 工具动作是不是单一清楚  
3. 产物结构是不是足够稳定  
4. provenance 有没有把关键过程记下来  
5. 哪一步如果失败，我现在知不知道该怎么改

如果这 5 件事里还有两三件说不清，那说明这次成功更多是“碰巧成了”。这不丢人，但它提醒你还不能急着往上叠复杂度。

## 什么样的首个 Agent 不适合现在做

为了避免第一次就被复杂度拖住，下面这几类任务通常不适合拿来做第一个 Agent：

- 同时读取很多来源，还要自己挑主次
- 一次调用多个外部服务
- 输出格式开放度很高，没有固定结构
- 结果对错需要主观判断，肉眼不容易验收

这些任务不是不能做，而是更适合等你先建立起“可验收闭环”之后再做。否则你会很容易把问题误会成“Agent 很难”，而不是“第一次任务选得太重”。

## 这一章和后面案例是什么关系

这一章其实是整个实战部分的地基。后面无论是对话 Agent、旅行助手，还是德州扑克多 Agent 系统，都会越来越复杂，但它们本质上都会继续复用这里建立起来的东西：

- 明确输入
- 明确动作
- 明确产物
- 明确验收
- 保留运行记录

也就是说，后面的复杂案例不是另起一套新逻辑，而是在这个最小闭环上逐层加东西。

## 这一章读完后，你应该能做到什么

读完这一章后，你至少应该能独立定义一个首个 Agent 任务，知道为什么它要小、为什么它要可验收、为什么它要留下 provenance。更重要的是，你应该能区分“看起来完成了”和“真的可以交付了”之间的差别。

只要这一步建立起来，后面的案例就不再只是演示，而会变成你已经有能力接住的真实工程练习。
