## 案例目标

设计一个多 Agent 德州扑克系统：你是主玩家，其他 Agent 是不同风格的玩家，系统负责状态同步、回合推进、决策记录和最终结算。

## 这一章要讲什么

- 为什么德州扑克很适合讲多 Agent
- 不同玩家 Agent 的角色与策略怎么设计
- 共享牌局状态怎么传递
- 多 Agent 协作与对抗如何同时存在

## 为什么最后一个案例要选德州扑克

如果前两个案例解决的是“一个 Agent 怎么完成任务”，那这一篇要解决的就是另一件更难的事：当一个任务里天然存在多个角色，而且每个角色既共享一部分信息，又保留一部分私有信息时，系统该怎么设计。

德州扑克特别适合拿来讲这个问题，因为它天然同时具备几种多 Agent 最核心的张力：有公共状态，有私有状态，有轮流行动，有明确规则，有竞争关系，也有隐性的协作关系。它不像旅行助手那样主要在“拆任务”，而是在逼你第一次正面处理“多角色系统如何共存”。

## 这个案例真正要学的不是牌，而是系统结构

很多人第一眼会把它看成一个好玩的游戏案例，但对 Agent 开发来说，这篇最重要的不是牌桌策略本身，而是它把多 Agent 的关键问题都压缩到了一个容易观察的环境里。

你会被迫回答这些问题：

- 谁知道什么
- 谁能做什么
- 谁什么时候发言
- 共享状态放在哪里
- 某个 Agent 的动作如何影响其他 Agent

只要这几个问题你开始能说清楚，多 Agent 就不再只是“多开几个角色一起聊天”，而开始真正像一个系统设计问题。

## 这个系统里至少有哪些角色

第一版完全不用做得太复杂，但至少可以有下面几类角色：

- 你自己：主玩家
- 若干玩家 Agent：代表不同风格对手
- 裁判或状态机：负责推进牌局、更新底池、检查规则、判定轮次

这一步非常关键，因为它提醒你，多 Agent 系统里并不是每个 Agent 都是“同一种角色”。有些角色是决策者，有些角色是执行者，有些角色本质上更像系统调度器。

也就是说，多 Agent 的关键不是“数量变多”，而是“职责开始分层”。

## 为什么必须区分公共状态和私有状态

这是这个案例最能教会人的一件事。很多人第一次做多 Agent，会默认所有角色都看同样的上下文，然后各自发表意见。但德州扑克这个场景会立刻告诉你，这么做是错的。

因为牌局里天然存在两类信息：

- 公共状态：公共牌、底池、当前轮次、谁已弃牌、当前下注额
- 私有状态：某个玩家自己的手牌、自己的策略倾向、自己的风险判断

如果你把所有状态都共享给所有 Agent，系统就不成立了；如果你完全不共享，大家又无法在同一局牌里行动。多 Agent 的设计难点，恰恰就在这个“共享到哪，保留到哪”的边界上。

## 状态同步为什么是这一页的主角

前面几篇已经讲过状态，但那时候更多是单 Agent 的上下文连续性。到了这个案例，状态开始变成整个系统的中轴，因为所有 Agent 都要围绕同一局牌来行动。

一个最小状态对象里，至少应该包含：

- 当前轮次
- 公共牌
- 底池大小
- 当前行动到谁
- 每个玩家是否仍在局内
- 每个玩家这一轮的动作历史

有了这层，玩家 Agent 才不是在各说各话，而是在同一个世界模型里做决定。没有这层，所谓“多 Agent”就只是多个独白。

## 为什么这里需要一个裁判或状态机

很多新手会下意识觉得，多 Agent 系统就是让多个角色轮流发言。但在真实系统里，通常还需要一个不负责“扮演角色”、而负责“维持秩序”的东西。

在这个案例里，这个东西可以叫：

- 裁判
- 游戏引擎
- 状态机
- 局面管理器

名字不重要，重要的是它承担的职责：

- 记录公共状态
- 决定当前轮到谁
- 检查动作是否合法
- 执行动作后的状态更新
- 最后进行结算

你会发现，这和前面旅行助手里隐含出现的“调度角色”是同一种问题，只是这里更明显。多 Agent 系统往往不是没有中心，而是有一个不直接决策、只负责协调和推进的中心。

## 不同玩家 Agent 应该怎么设计

如果所有玩家 Agent 的行为模式都一样，这个系统会很快失去意义。因为那样你只是复制了多个相同角色，并没有真正引入多 Agent 的差异性。

第一版最适合做的，是给不同玩家设置非常清楚的风格差异，例如：

- 紧凑保守型：只在手牌较强时积极下注
- 激进压迫型：倾向于高压和加注
- 诡计试探型：喜欢通过虚张声势扰动判断

注意，这里的重点不是“策略多专业”，而是角色差异要足够稳定。只有差异稳定，你才能观察到同一公共状态在不同 Agent 眼里为什么会导向不同动作。

## 多 Agent 不是一起合作，而是一起存在

这是这一页最容易误解的地方。很多人一听“多 Agent”，会自动想到多个角色一起分工合作，像团队一样完成一个共同目标。但德州扑克会提醒你，多 Agent 完全可能同时包含合作和对抗。

在这张牌桌上：

- 所有人都共享同一套规则
- 所有人都依赖同一个状态机
- 所有人都必须遵守同样的轮次推进

这是“协作”的部分。

但同时：

- 每个玩家都要争夺同一个结果
- 每个玩家都在做自己的利益判断
- 每个玩家的动作都会影响别人

这是“对抗”的部分。

也就是说，多 Agent 的本质不是“关系友好”，而是“多个可行动角色同时存在于同一个可推进系统里”。

## 一个最小回合流程可以长什么样

为了把这个案例讲清楚，第一版完全可以只做一个最小回合流程：

1. 状态机公布当前公共状态  
2. 当前轮次对应的玩家 Agent 读取可见状态  
3. 该玩家输出动作：`fold` / `call` / `raise`  
4. 状态机检查动作是否合法  
5. 状态机更新底池、行动顺序和轮次记录  
6. 下一位玩家继续

这个流程看起来简单，但它已经完整体现了多 Agent 系统的几个核心：角色轮转、公共状态推进、动作影响后续、系统中心负责一致性。

## 一个最小状态结构示例

如果把牌局状态写成结构化对象，第一版可以长这样：

```json
{
  "stage": "turn",
  "community_cards": ["A♠", "10♦", "10♣", "4♥"],
  "pot": 320,
  "current_bet": 40,
  "current_player": "agent_b",
  "players": {
    "you": { "active": true, "chips": 860, "private_cards": ["K♠", "J♠"] },
    "agent_a": { "active": true, "chips": 920, "style": "tight" },
    "agent_b": { "active": true, "chips": 780, "style": "aggressive" },
    "agent_c": { "active": false, "chips": 1000, "style": "tricky" }
  }
}
```

这里最重要的不是字段长得多漂亮，而是你已经开始把“牌桌”从一段故事，转成一个所有 Agent 都能围绕其行动的共享状态对象。

## 一个最小 Prompt 结构

如果给某个玩家 Agent 写 Prompt，第一版可以非常直接：

```md
你是牌桌上的一个玩家，风格是“激进压迫型”。

你的职责：
- 根据当前牌局公共状态和你的角色风格做出行动
- 行动只能是 `fold`、`call` 或 `raise`
- 给出一行简短理由

你的边界：
- 只能基于你可见的牌局状态行动
- 不能读取其他玩家的私有手牌
- 不能跳过轮次或修改公共状态
```

你会发现，这和前面对话 Agent、旅行助手的写法其实是同一种结构。只是现在，Prompt 不再只是定义一个“任务助手”，而是在定义牌桌上的一个局内角色。

## 这个案例怎么验收

这一页不需要你真的做出一套完整扑克 AI，验收重点也不在牌技高低，而在系统有没有成立。最值得检查的地方通常是：

1. 每个角色的职责是否清楚  
2. 公共状态和私有状态是否区分清楚  
3. 回合推进是否一致  
4. 某个 Agent 的动作是否真的会改变后续状态  
5. 最后能否回放一整局记录

只要这几件事成立，这个案例就已经非常有教学价值。因为它让你第一次真正看见“多个智能角色如何共同构成一个可运行系统”。

## 一局记录为什么是必要交付物

这个案例和前面几篇一样，不能只停留在“概念理解”。为了让它可复盘，最好一定要有一份完整对局记录。它可以很简单，但至少应该包含：

- 初始状态
- 每轮轮到谁
- 每个玩家做了什么动作
- 动作后公共状态如何变化
- 最终结算结果

这份记录的价值非常大。它会把一个抽象的多 Agent 系统，变成一个可以逐步回放、逐步解释、逐步改进的具体对象。

## 最常见的坑

第一次做多 Agent，最容易踩的坑通常有 5 个：

- 所有角色共享了不该共享的私有信息
- 没有状态机，导致轮次和规则混乱
- 每个 Agent 只是在“发表看法”，没有真实动作约束
- 角色风格写了很多，但行为没有稳定差异
- 最后没有留下完整牌局记录，无法复盘

这些问题会让系统看起来很热闹，但其实没跑起来。真正的多 Agent 不是多几个角色一起说话，而是多几个角色一起受规则约束、一起推动系统状态变化。

## 为什么这篇是整套课的终点

到这里，你会发现前面的东西都在这里汇合了。最小骨架在这里仍然成立，只是从一个 Agent 扩展到多个角色；Prompt 契约仍然有用，只是每个角色都要有自己的契约；工具和状态仍然重要，只是现在状态从单体上下文变成了共享世界模型。

也就是说，这篇不是另起一套新方法，而是把整套课前面讲过的东西，放进一个更复杂、更能体现系统性的场景里。你能把这一篇看懂，说明你已经不只是在学“怎么写一个会回答的 Agent”，而是在开始学“怎么设计一个由多个角色组成的可运行系统”。

## 这一章读完后，你应该能做到什么

读完这一章后，你至少应该能判断一个多 Agent 场景里有哪些角色，哪些信息该共享，哪些信息该私有，为什么需要状态机，以及为什么“完整记录一局过程”比“让角色看起来更聪明”更重要。

只要这一步建立起来，后面你再去看更复杂的多 Agent 产品或框架时，就不会只看到一堆名词，而会知道它们到底在试图解决哪一类系统问题。
