## 案例目标

做一个最小但真正成立的对话 Agent：不是随便聊天，而是围绕一个明确任务域，给出稳定、结构化的回应。

## 这一章要讲什么

- 角色怎么定义
- 对话上下文怎么控
- 结构化输出怎么设计
- 为什么这个案例比“普通聊天”更像 Agent

## 为什么第一个案例先从对话 Agent 开始

它看起来最轻，但其实很适合当第一篇实战。因为对话天生就是最容易上手的交互形式，你不需要先理解复杂外部系统，也不需要一开始就接很多工具，就能先把角色、边界、上下文和输出结构这些 Agent 的核心部件练起来。

更重要的是，这个案例能帮你第一次真正看到一件事：不是所有“会说话的 AI”都叫 Agent。只有当对话围绕一个明确任务域展开，且每次回应都有稳定目标和结构时，它才开始像一个工作系统。

## 这个案例要做成什么

这次我们不做“万能聊天机器人”，而是做一个任务域明确的小 Agent。你可以把它理解成一个带固定职责的对话伙伴，例如：

- 面向创业者的选题整理助手
- 面向产品团队的需求澄清助手
- 面向学习者的概念解释助手

它们的共同点不是“更聪明”，而是都只服务一个相对清楚的场景。也正因为场景够窄，你才能判断它到底有没有稳定发挥。

## 对话 Agent 和普通聊天最大的差别

普通聊天的重点是自然、流畅、像人在交流。对话 Agent 的重点则是稳定地完成某一类任务。它当然也会聊天，但聊天在这里不是目的，而是完成任务的交互方式。

所以一个真正成立的对话 Agent，至少要回答清楚 4 件事：

- 它是谁
- 它负责什么
- 它不负责什么
- 它每次回答应该长成什么样

只要这 4 件事没写清楚，它就很容易从一个“任务型对话 Agent”退化回“什么都聊一点的普通聊天框”。

## 第一步不是写人设，而是先定任务域

很多人做对话 Agent 时，第一反应是先写一个很长的人设，比如口吻、性格、说话风格、情绪倾向。但对实战来说，更应该先写清楚的是任务域。

比如“你是一个温柔专业的 AI 助手”几乎没什么约束力，因为它没有告诉系统该解决哪类问题。反过来，“你是一个帮助用户整理内容选题的助手，只负责把模糊想法整理成标题、角度和提纲，不负责写完整文章”就已经清楚得多。

任务域一旦清楚，人设只是补充；任务域不清楚，再完整的人设也只能让它变得更像一个会表演的角色。

## 角色要怎么定义才有用

一个有用的角色定义，最好同时包含下面几层：

- 它服务谁
- 它擅长什么
- 它使用什么回答风格
- 它不越过哪些边界

例如：

```md
你是一个“内容选题整理助手”。

你的职责：
- 帮用户把模糊想法整理成明确选题
- 给出适合展开的角度
- 输出结构化提纲

你的边界：
- 不直接代写完整文章
- 不输出与选题无关的闲聊内容
- 如果用户信息不足，先追问，不硬猜
```

这样写的价值是，它把角色从“抽象人格”变成了“任务位置”。

## 边界决定它会不会漂

对话 Agent 最容易出的问题不是不会回答，而是越聊越飘。一开始还在任务域里，聊几轮之后就开始泛化、发散、顺着用户每一句话滑走，最后什么都说一点，但不再稳定完成那件核心任务。

所以边界是这个案例最关键的一层。你要提前写清：

- 哪类问题可以回答
- 哪类问题需要拒答或转向
- 信息不足时先追问还是先给草稿
- 回答里允许不允许引入额外推断

只要边界不清，对话体验表面上可能很顺，但实际很难复用，也很难验收。

## 上下文不是越多越好，而是要知道记什么

很多人一提到对话 Agent，就会立刻想到“记忆”。但第一版系统里，最重要的不是记很多，而是先知道哪些东西该被记住。

对一个任务型对话 Agent 来说，真正值得保留的上下文通常是：

- 当前任务目标
- 用户已经确认过的偏好
- 当前轮次已经收集到的关键信息
- 已经生成过的中间结构

而很多不重要的闲聊、重复表达、情绪性内容，未必需要强记。因为一旦什么都记，系统反而更容易失焦。对话 Agent 的上下文控制，本质上是在维持任务连续性，而不是在模拟“记性特别好的人”。

## 为什么结构化输出很重要

如果这个案例只是“陪用户聊聊”，那它和普通聊天差别就不大了。真正让它进入 Agent 状态的，是你给每次回答规定了相对稳定的结构。

比如一个“选题整理助手”可以固定输出：

- 你的核心想法
- 可以展开的 3 个角度
- 一个推荐标题
- 下一步需要补的信息

这样做的好处非常大。它让每次输出都可以被比较、被复盘、被继续加工。你不再只是觉得“这次回答还不错”，而是能明确看到它有没有稳定完成自己的职责。

## 一个最小输出模板

假设我们做的是“内容选题整理助手”，那么第一版完全可以先固定成下面这个结构：

```md
## 你的想法被整理成什么

### 核心主题

### 3 个可展开角度

### 推荐标题

### 下一步还缺什么信息
```

这套模板并不复杂，但它已经足够帮助你判断：这次回答是不是稳定、是不是越界、是不是还能继续往下接。

## 一个最小 Prompt 示例

把这个案例压成最小版本，可以写成下面这样：

```md
你是一个“内容选题整理助手”。

你的职责：
- 帮用户把模糊想法整理成明确选题
- 提炼核心主题
- 给出 3 个可展开角度
- 推荐一个标题

你的边界：
- 不直接代写完整文章
- 不回答与选题无关的话题
- 如果用户提供的信息不足，先提出需要补充的问题

输出结构固定为：
1. 核心主题
2. 3 个可展开角度
3. 推荐标题
4. 下一步还缺什么信息
```

到这里，你已经不是在单纯“让 AI 帮我想想”，而是在定义一个稳定的对话工作单元。

## 怎么判断它已经不是普通聊天

最简单的判断方法，不是看它说话像不像人，而是看你能不能连续问 3 轮相似问题，它依然保持：

- 角色不变
- 任务域不变
- 输出结构不变
- 边界不乱跑

如果这 4 件事能稳住，它就已经开始具备 Agent 的味道了。反过来，如果它一会儿像选题助手，一会儿又跑去写诗、安慰情绪、讲泛知识，那说明它还只是一个泛聊天入口。

## 这个案例的验收方式

这一页最重要的不是把它做得多花，而是把验收做得足够简单清楚。你可以直接用下面几条来检查：

1. 相似输入下，回答结构是否稳定  
2. 面对越界问题时，是否会收回到自己的任务域  
3. 信息不足时，是否会先追问，而不是直接乱猜  
4. 输出里是否固定包含你要求的字段

这类验收不需要复杂工具，肉眼就能完成。也正因为它容易检查，所以特别适合做第一个实战案例。

## 一组最小测试对话

你可以用下面这组输入来测试它：

```md
用户：
我最近想做一个关于独立开发的内容，但方向还有点散。

期待输出：
- 提炼出一个核心主题
- 给出 3 个展开角度
- 给一个推荐标题
- 告诉我还缺什么信息
```

再补一个越界测试：

```md
用户：
先别聊选题了，你给我写一首诗吧。

期待表现：
- 不直接切到无关任务
- 把对话拉回“选题整理”职责
```

这两组测试已经足够让你看出它到底是不是一个稳定的任务型对话 Agent。

## 这个案例最常见的问题

第一次做对话 Agent，最常见的坑通常有 4 个：

- 角色写得很热闹，但任务域很空
- 没写边界，导致越聊越散
- 没有固定输出结构，每轮回答长相完全不同
- 觉得“自然”比“稳定”更重要

这些问题会让系统看起来很会聊，但很难真正服务一个具体目标。你后面一旦想把它接到更大案例里，就会发现根本没法复用。

## 为什么这个案例是后面复杂案例的起点

对话 Agent 看起来简单，但它其实先把很多核心能力练掉了：角色定义、边界控制、上下文取舍、结构化输出、简单验收。后面的旅行助手和多 Agent 系统虽然更复杂，本质上还是会继续用到这些东西。

所以这篇不是一个“热身 demo”，而是整套实战的第一块地基。你把这块地基打稳，后面加工具、加数据源、加多个 Agent，系统才不会一上来就散。

## 这一章读完后，你应该能做到什么

读完这一章后，你至少应该能独立写出一个任务域清楚的对话 Agent 定义，知道怎么给它设边界、控上下文、定输出结构，也知道怎么用几轮最小测试去判断它是否稳定。

只要这一步站住，后面你再做“智能旅行助手”时，就不会只是把更多工具堆上去，而会知道每一层新能力该挂在什么地方。

## 继续阅读

对话 Agent 解决的是最小任务型交互。继续读 `21-travel-assistant.md`，你会看到同样的骨架怎样被推进到真实世界任务里，开始处理条件收集、外部信息和结构化交付。
