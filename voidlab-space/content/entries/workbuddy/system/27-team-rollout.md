团队落地最容易犯的错，是把“我自己已经用顺了”误认为“团队可以直接复制”。个人提效靠的是熟练度和隐性经验，团队落地靠的是**边界、模板、权限、验收、反馈回路**。如果这些没被显式化，团队会把同一套工具用成十种完全不同的东西。

这篇不是讲“怎么安利同事”，而是讲：怎样把一次个人成功收成一套多人可运行的协作系统。

## 一句话结论

团队落地的核心不是“让更多人都开始用”，而是**让更多人按同一套边界和交付标准稳定地产出**。所以真正要推广的不是工具本身，而是“可复制的工作流”。

## 团队视角下最重要的三件事

- 权限边界
- 交付标准
- 失败回退

我建议再补两件事，不然团队很难跑稳：

- 角色分层：谁能设计流程，谁只负责执行
- 反馈机制：问题如何被收集、归因、再写回系统

更具体一点，变化通常发生在四个层面：

- **目标层**：从“我想更快”变成“团队要更稳定、更一致”
- **权限层**：从“我自己知道风险”变成“不同人要不同边界”
- **交付层**：从“我觉得行”变成“别人也能验收”
- **系统层**：从“个人手感”变成“文档、模板、日志、回退”

## 团队落地的四阶段

我建议团队不要一上来全员铺开，而是按下面四阶段推进：

### 阶段 1：个人样板跑通

先用一个人、一个场景、一个模板，把流程跑通并留下完整产物：

- 输入材料长什么样
- 输出文件长什么样
- 验收标准是什么
- 出错时如何回退

这一阶段的目标不是“效率最大化”，而是把系统的第一份真相源建立起来。

### 阶段 2：小范围试点

选 2~5 个人做试点，要求他们用同一模板执行同一类任务。观察三件事：

- 是不是每个人都能看懂说明
- 是不是每个人都能产出同结构结果
- 是不是会在同一位置翻车

这一阶段最重要的是收集“系统性摩擦”，而不是个体吐槽。

### 阶段 3：模板化与分层权限

当同一类任务连续跑通后，把它们沉淀成：

- 模板库
- Skill / 工作流说明
- 权限分层（默认权限 / 完全访问 / 只读连接器 / 草稿区写入）

这一步完成后，团队才真正拥有了“可以复制”的基础设施。

### 阶段 4：团队推广与回填

推广时不要用“培训一次就结束”的思路，而要建立固定回填：

- 哪类任务最常用
- 哪类任务最常失败
- 哪些规则需要更新
- 哪些模板应该淘汰

这样你推广的是一个会迭代的系统，而不是一套静态教程。

## 角色分层：谁有权做什么

团队落地最怕权限混乱。推荐最小分层如下：

| 角色 | 典型人群 | 可以做什么 | 不该做什么 |
|---|---|---|---|
| Designer | 流程设计者 / 负责人 | 设计模板、改规则、选连接器、定义验收 | 不直接代表团队做全部执行 |
| Operator | 日常执行者 | 按模板跑任务、交付结果、反馈问题 | 随意改模板或权限边界 |
| Reviewer | 审核者 / 经理 | 对结果验收、批准升级权限、判断是否发布 | 把“我觉得还行”当成验收标准 |
| Admin | 系统维护者 | 管理权限、连接器、日志、回退策略 | 代替业务定义任务目标 |

这张表的意义是：不同人对系统的影响面不同，权限必须匹配职责。

## 团队落地最先要固定的 5 个资产

如果你只做一件事，请优先把下面 5 个资产固定下来：

1. `任务模板`：同类任务怎么写目标/输入/约束/输出/验收  
2. `交付样例`：合格结果长什么样  
3. `权限说明`：谁能开哪些权限/连接器  
4. `回退手册`：失败了怎么退回安全状态  
5. `问题日志`：团队最常见问题与对应修复方式

没有这 5 项，团队永远只能靠口口相传。

## 验收：团队不是“会不会用”，而是“能不能稳定交付”

团队落地不能用“有多少人打开过 WorkBuddy”来判断成功，应该用下面这些指标：

- 模板采用率：多少任务按标准模板执行
- 一次通过率：第一次交付就通过验收的比例
- 回退率：多少任务需要进入手动 fallback
- 规则更新率：团队反馈有没有真正写回模板/Skill/手册

这组指标更接近“系统成熟度”，而不是“使用热情”。

### 模板 B：团队推广任务说明（可直接复制）

```txt
目标：把一个已经被个人跑通的 WorkBuddy 工作流沉淀为团队可复用系统，并在小范围内试点运行。

输入：
- 已跑通的任务样例
- 对应模板文件
- 验收标准
- 当前权限/连接器配置

动作：
1) 抽取团队必须共享的资产：模板、交付样例、权限说明、回退手册、问题日志
2) 设计最小角色分层：Designer / Operator / Reviewer / Admin
3) 选择 2~5 人试点，并输出团队试点卡
4) 建立反馈回填机制：问题如何记录、谁更新模板、多久复盘一次
5) 输出 rollout 文档：如何上线、如何培训、如何回退

约束：
- 不要一上来全员推广，先小范围试点
- 不允许口头传递关键规则，必须文件化
- 所有高风险动作必须有 fallback

输出：
- output/team-rollout-plan.md
- output/pilot-card.md
- output/permission-matrix.md
- output/fallback-runbook.md

验收：
- 新人只看文档就能按模板完成一次任务
- 权限边界与升级条件明确
- 出错时知道退回哪里，不需要临场猜
```

## 常见坑与排查

- 一上来全员铺开：先试点，否则错误会被放大
- 把成功归因于“这个同事比较会用”：说明系统没被显式化；补模板与样例
- 权限开得太大：团队里一定要分层，不同角色权限不同
- 培训完没有回填：没有问题日志与规则更新，团队只会重复踩坑
