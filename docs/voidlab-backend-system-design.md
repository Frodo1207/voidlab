# VOIDLAB 后台系统设计文档

## 1. 文档目的

本文档用于在前端 Demo 已基本清晰的前提下，反向定义 VOIDLAB 的后台系统、后端服务与一期实施范围。

这不是一份通用 CMS 设计文档，而是一份面向当前项目阶段的业务系统设计文档。核心目标是帮助团队回答三个问题：

1. VOIDLAB 现在到底要做一个什么系统
2. 第一阶段后端应该支撑哪些业务动作
3. 后台、后端、前台之间应该如何协同

## 2. 当前阶段判断

### 2.1 已经明确的部分

前端 Demo 已经把核心业务对象和页面关系表达出来，当前业务主线包括：

- 首页品牌与服务表达
- Insights 资讯内容运营
- Events 活动运营
- Builders 社交网络 / 成员展示
- Contact 联系与合作承接

从产品视角看，前端不是单纯官网，而是一个围绕 AI 社区展开的业务门户。

### 2.2 当前系统现状

当前仓库可理解为：

- `apps/web`：高完成度前台 Demo
- `apps/admin`：后台骨架
- `apps/api`：后端基础服务骨架

当前业务数据主要仍由前端本地静态数据驱动，后台与后端尚未接入真实业务闭环。

### 2.3 当前阶段的正确目标

现阶段不应该先做“大而全后台”，而应该先完成：

**从前台展示系统，过渡到可运营、可维护、可转化的业务系统。**

## 3. 系统目标

VOIDLAB 后台系统第一阶段的核心目标，不是做一个“内容管理工具”，而是做一个围绕社区运营的轻量业务中台。

第一阶段要支撑四条主链路：

1. 内容链路：选题 -> 编辑 -> 发布 -> 前台展示
2. 活动链路：创建活动 -> 发布 -> 报名承接 -> 活动回顾
3. 成员链路：Builder 建档 -> 上架展示 -> 合作发起
4. 线索链路：Contact / Event / Builder 的外部意向统一沉淀

## 4. 产品定位

### 4.1 系统不是什么

VOIDLAB 后台系统不应被定义为：

- 通用企业官网 CMS
- 大而全的多租户平台
- 复杂社交平台后端
- 一开始就覆盖所有运营可能性的超级后台

### 4.2 系统是什么

VOIDLAB 后台系统应被定义为：

**一个服务于社区内容、活动运营、成员网络和合作转化的运营中台。**

其本质是帮助团队高效完成：

- 内容发布
- 活动组织
- 成员展示
- 线索管理
- 媒体管理
- 站点配置

## 5. 目标用户与后台角色

第一阶段建议只定义三类后台角色，避免过早设计复杂权限系统。

### 5.1 Admin

职责：

- 拥有全部管理权限
- 管理站点配置
- 管理账号与基础权限
- 查看全部业务数据

### 5.2 Editor

职责：

- 管理资讯内容
- 管理活动内容
- 管理 Builder 展示资料
- 不负责系统级配置

### 5.3 Ops / Sales

职责：

- 主要查看与处理线索
- 更新跟进状态
- 记录沟通结果
- 不直接编辑核心内容

## 6. 一期业务模块

第一阶段建议只做 6 个模块。

### 6.1 站点配置模块

用于承接首页与全局内容配置，避免反复改前端代码。

建议覆盖：

- 首页 Banner 主标题 / 副标题 / CTA
- 首页精选内容配置
- 联系方式配置
- 导航与页脚基础配置
- 联系页入口配置

### 6.2 资讯管理模块

用于承接 Insights 页面。

建议覆盖：

- 文章创建 / 编辑 / 删除
- 草稿 / 已发布状态
- 分类、标签、受众、发布时间
- 封面图与摘要
- 是否精选
- 原文来源与来源链接

### 6.3 活动管理模块

用于承接 Events 页面。

建议覆盖：

- 活动创建 / 编辑 / 删除
- 活动时间、地点、城市、状态
- 活动类型
- 封面图、摘要、详情
- 报名链接或报名表单
- 活动结束后的回顾内容

### 6.4 Builder 管理模块

用于承接社交网络页面。

建议覆盖：

- 成员基础资料
- 角色、城市、技能、关注方向
- 合作方式
- 可联系状态
- 是否 featured
- 上架 / 下架

### 6.5 Leads 线索模块

这是第一阶段最关键的业务模块之一。

所有对外意向入口都应该尽量统一沉淀进 Leads：

- Contact 页面提交
- 活动报名 / 预约
- Builder 合作发起
- 后续可能接入邮箱或表单工具导入

建议覆盖：

- 线索来源
- 联系人信息
- 意向类型
- 跟进状态
- 跟进记录
- 转化结果

### 6.6 媒体资源模块

用于管理图片与附件资源。

建议覆盖：

- 图片上传
- 文件地址管理
- 引用关系记录
- 封面图选择
- 基础文件元信息

## 7. 核心业务对象

从前端 Demo 反推，第一阶段的核心数据实体建议如下：

- `users`
- `articles`
- `article_categories`
- `article_tags`
- `events`
- `builders`
- `leads`
- `lead_logs`
- `media_assets`
- `site_configs`

## 8. 状态设计

产品系统设计里，最重要的不是“有没有表”，而是“业务对象是否有生命周期”。

### 8.1 Article 状态

- `draft`
- `scheduled`
- `published`
- `archived`

### 8.2 Event 状态

- `draft`
- `upcoming`
- `live`
- `ended`
- `archived`

### 8.3 Builder 状态

- `draft`
- `pending_review`
- `published`
- `hidden`

### 8.4 Lead 状态

- `new`
- `contacted`
- `following`
- `converted`
- `invalid`

## 9. 核心业务流程

### 9.1 资讯发布流程

1. 编辑创建文章草稿
2. 上传封面与补充摘要
3. 设置分类、标签、受众
4. 标记是否精选
5. 发布到前台

交付结果：

- 内容进入 Insights 列表或精选位
- 可在详情页展示来源、标签与正文

### 9.2 活动发布流程

1. 运营创建活动
2. 配置时间、地点、状态、封面
3. 填写活动详情与报名方式
4. 发布到前台
5. 活动结束后补活动回顾

交付结果：

- 活动在前台列表可见
- 用户可通过活动页面进入报名或预约入口

### 9.3 Builder 上架流程

1. 录入 Builder 档案
2. 配置角色、城市、能力、合作方式
3. 标记是否可联系、是否 featured
4. 审核后上架

交付结果：

- Builder 在社交网络页和详情页展示
- 用户可从详情页发起合作

### 9.4 Leads 统一沉淀流程

1. 用户从 Contact / Event / Builder 发起意向
2. 系统自动创建 Lead
3. 自动记录来源渠道
4. 运营或销售开始跟进
5. 更新状态与结果

交付结果：

- 所有对外合作意向统一进入一个线索池
- 后续可做统计、归因和转化分析

## 10. 一期必须打通的闭环

第一阶段最重要的不是页面数量，而是闭环数量。

建议先打通以下 4 个闭环：

### 10.1 内容闭环

后台发文 -> 前台展示 -> 用户阅读

### 10.2 活动闭环

后台建活动 -> 前台展示 -> 用户报名 / 预约

### 10.3 Builder 闭环

后台建档 -> 前台展示 -> 用户发起合作

### 10.4 Leads 闭环

所有入口意向 -> Leads -> 跟进 -> 状态更新

## 11. 后端架构建议

基于当前仓库和项目规模，建议采用轻量但清晰的分层。

### 11.1 推荐分层

- Handler / API 层：接收 HTTP 请求
- Service 层：承接业务规则
- Repository 层：负责数据访问
- Storage / Infra 层：SQLite、MinIO、鉴权等基础设施

### 11.2 推荐 API 域

- `/api/v1/auth`
- `/api/v1/articles`
- `/api/v1/events`
- `/api/v1/builders`
- `/api/v1/leads`
- `/api/v1/media`
- `/api/v1/site-config`

### 11.3 技术建议

第一阶段建议：

- 后端：Gin
- 数据库：SQLite
- 媒体存储：MinIO
- 管理端鉴权：基于 Session 或 JWT 的轻量实现

SQLite 在当前阶段是合适的，原因是：

- 当前业务量有限
- 开发与部署成本低
- 易于快速验证后台闭环

等系统进入更稳定的运营期，再考虑迁移到 Postgres。

## 12. 一期不建议做的内容

为了控制项目复杂度，以下内容建议明确排除在一期之外：

- 复杂 RBAC 权限系统
- 多组织 / 多租户
- 评论系统
- 自动化营销系统
- 高级统计报表
- 消息通知中心
- 工作流编排引擎

这些能力不是没有价值，而是不适合在当前阶段优先建设。

## 13. 一期页面建议

后台第一阶段建议有如下页面：

1. 登录页
2. 仪表盘首页
3. 资讯列表页
4. 资讯编辑页
5. 活动列表页
6. 活动编辑页
7. Builder 列表页
8. Builder 编辑页
9. Leads 列表页
10. Lead 详情页
11. 媒体库页
12. 站点配置页

其中优先级最高的是：

- 资讯列表 / 编辑
- 活动列表 / 编辑
- Builder 列表 / 编辑
- Leads 列表

## 14. 项目分期建议

### Phase 1：内容可运营

目标：

- 后台登录
- 资讯管理
- 活动管理
- Builder 管理
- 媒体上传
- 前台改为从 API 读取数据

### Phase 2：线索闭环

目标：

- Contact 表单入库
- Builder 合作入库
- 活动报名 / 预约入库
- Leads 跟进与状态管理

### Phase 3：站点配置化

目标：

- 首页内容配置化
- 联系方式配置化
- 精选内容配置化
- 部分页面模块开关化

### Phase 4：运营增强

目标：

- 数据统计
- 发布排期
- 审核流
- 更细权限

## 15. 推荐实施顺序

从项目管理视角，建议按“先打通闭环，再增强体验”的顺序推进。

### 第一步：明确数据模型

先确定：

- 核心实体
- 字段边界
- 状态设计
- 模块关系

### 第二步：先做 Admin 最小闭环

先不要急着做漂亮后台，而是先能完成：

- 登录
- 文章 CRUD
- 活动 CRUD
- Builder CRUD
- Leads 查看

### 第三步：前台接 API

当前前端 Demo 的静态数据应逐步切换为 API 数据，先完成：

- Insights
- Events
- Builders

### 第四步：再做 Contact / Leads 联动

让前台从“可看”变成“可转化”。

## 16. 成功标准

如果一期做完，应该达到以下标准：

1. 非开发人员可以通过后台发资讯、发活动、上架 Builder
2. 前台不再依赖手改代码更新核心内容
3. Contact / Event / Builder 的意向可以统一进入 Leads
4. 团队可以清楚知道每条线索来自哪里、当前处于什么状态

## 17. 一句话总结

VOIDLAB 当前最适合建设的，不是一个大而全的 CMS，也不是一个复杂平台，而是一个：

**围绕内容、活动、成员网络和合作转化的轻量运营中台。**

第一阶段最重要的任务，是把前端 Demo 里已经清晰的业务对象，真正接成一个可运营、可维护、可转化的系统。
