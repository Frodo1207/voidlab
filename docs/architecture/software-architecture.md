# VOIDLAB 软件架构文档

## 1. 文档目标

本文档用于定义 VOIDLAB 的整体软件架构，作为后续各阶段需求文档和设计文档的上位约束。

本文档重点回答四个问题：

1. 系统由哪些部分构成
2. 每一层分别承担什么职责
3. 当前阶段应优先建设哪些能力
4. 后续 AI Agent Skill 和知识库应如何接入

## 2. 架构目标

VOIDLAB 当前的软件架构目标不是追求“大而全”，而是支撑以下演进路径：

1. 前端 Demo 驱动业务澄清
2. 后台与后端承接当前业务闭环
3. 系统进入稳定运营状态
4. AI Agent 通过 Skill 接管部分标准化运营动作
5. 知识库作为长期资产与 Agent 增强层接入

因此，架构设计需要满足三个原则：

- 先支撑当前业务，不提前过度设计
- 结构要清晰，方便后续加模块
- 预留 Agent 与知识库接入点

## 3. 整体架构分层

建议整体按五层设计：

1. 展示层
2. 管理层
3. API 与应用服务层
4. 数据与存储层
5. 智能扩展层

### 3.1 展示层

对应：

- `apps/web`

职责：

- 承接官网前台页面
- 展示资讯、活动、Builder、联系信息
- 承接用户阅读、报名、合作发起等外部动作

### 3.2 管理层

对应：

- `apps/admin`

职责：

- 承接后台管理操作
- 提供内容、活动、Builder、Leads、站点配置管理能力
- 后续作为 AI Skill 的受控操作面

### 3.3 API 与应用服务层

对应：

- `apps/api`

职责：

- 提供统一 API
- 实现业务规则
- 执行状态流转
- 校验输入、鉴权、审计、错误处理

### 3.4 数据与存储层

组成：

- SQLite
- MinIO

职责：

- 持久化业务数据
- 存储媒体资源
- 为前台展示、后台运营和 Agent 操作提供统一数据基础

### 3.5 智能扩展层

组成：

- AI Agent Skill
- 知识库模块

职责：

- 把后台标准动作开放为结构化能力
- 为 Agent 提供检索、生成、填充和辅助运营能力

## 4. 当前系统边界

### 4.1 当前主业务域

当前系统应先围绕以下业务域展开：

- Insights
- Events
- Builders
- Leads
- Site Config
- Media Assets

### 4.2 暂不纳入核心范围

当前阶段不纳入核心范围的内容：

- 社区即时互动系统
- 用户评论系统
- 多租户平台
- 复杂审批流
- 自动营销平台

## 5. 推荐后端分层

建议 `apps/api` 采用如下结构：

- `cmd/`
- `internal/http/`
- `internal/service/`
- `internal/repository/`
- `internal/domain/`
- `internal/storage/`
- `internal/config/`

### 5.1 HTTP 层

职责：

- 路由注册
- 请求解析
- 响应格式化
- 鉴权入口

### 5.2 Service 层

职责：

- 承接业务逻辑
- 实现发布规则、状态变更、线索归因
- 屏蔽底层数据存储细节

### 5.3 Repository 层

职责：

- 与 SQLite 打交道
- 实现业务对象的查询、写入、更新

### 5.4 Domain 层

职责：

- 定义核心实体
- 定义状态枚举
- 定义基础业务约束

### 5.5 Storage 层

职责：

- 数据库连接
- MinIO 文件存储
- 基础迁移和初始化

## 6. 推荐前后端关系

### 6.1 前台 `apps/web`

前台只负责：

- 渲染页面
- 获取 API 数据
- 提交表单
- 展示静态和动态内容

前台不应继续长期承担：

- 业务主数据定义
- 运营数据维护
- 内容手工硬编码

### 6.2 后台 `apps/admin`

后台负责：

- 运营录入
- 内容管理
- 状态流转
- Leads 跟进
- 配置维护

### 6.3 API `apps/api`

API 负责成为前台、后台、Skill 三者之间的统一中间层。

即：

- 前台不直接碰数据库
- 后台不直接碰数据库
- Agent Skill 也不直接碰数据库

三者都应该通过 API 进行受控访问。

## 7. 核心数据对象

建议优先建设以下实体：

- `users`
- `articles`
- `article_tags`
- `events`
- `builders`
- `leads`
- `lead_logs`
- `media_assets`
- `site_configs`

这些对象足以支撑当前业务阶段。

## 8. API 域划分建议

建议 API 按业务域拆分：

- `/api/v1/auth`
- `/api/v1/articles`
- `/api/v1/events`
- `/api/v1/builders`
- `/api/v1/leads`
- `/api/v1/media`
- `/api/v1/site-config`

后续扩展：

- `/api/v1/knowledge-base`
- `/api/v1/agent-actions`

## 9. 架构演进路径

### 9.1 第一阶段

以后台最小可用为目标：

- 登录
- 内容 CRUD
- 活动 CRUD
- Builder CRUD
- 媒体上传

### 9.2 第二阶段

以当前业务闭环为目标：

- 前台全部切 API
- Leads 统一沉淀
- Contact / Event / Builder 三个入口统一接入

### 9.3 第三阶段

以稳定运营为目标：

- 状态流
- 配置化
- 基础权限
- 操作日志

### 9.4 第四阶段

以 AI Skill 接入为目标：

- 标准动作 API
- 明确权限边界
- 结构化输入输出
- 可审计

### 9.5 第五阶段

以知识沉淀与智能增强为目标：

- 知识库模块
- 文档切片与检索
- Agent 检索增强

## 10. AI Agent Skill 接入原则

Skill 不应该绕过后台系统，而应该建立在稳定的软件架构之上。

接入原则如下：

1. 只调用标准 API
2. 只操作被允许的业务对象
3. 所有动作可审计
4. 输入输出尽量结构化
5. 失败时可定位和回滚

推荐 Skill 第一版支持：

- 创建文章
- 更新文章
- 创建活动
- 更新 Builder
- 上传媒体
- 查询 Leads
- 更新 Leads 状态

## 11. 知识库接入原则

知识库明确作为最后阶段能力，不进入当前业务核心阻塞路径。

知识库接入后应主要服务于：

- 运营知识沉淀
- 内容资产复用
- Agent 检索增强
- 标准 SOP 存档

知识库不应影响当前主业务系统的稳定运行。

## 12. 当前推荐技术路线

- 前台：Vue 3 + Vue Router
- 后台：Vue 3 + Element Plus + Pinia
- 后端：Gin
- 数据库：SQLite
- 文件存储：MinIO

当前阶段这条路线的优势是：

- 开发速度快
- 结构简单
- 部署成本低
- 易于快速验证业务模型

## 13. 架构成功标准

如果整体架构设计合理，应该达到：

1. 当前业务模块可以独立演进
2. 前台不再依赖静态硬编码维护核心数据
3. 后台成为唯一运营入口
4. API 成为统一能力中台
5. Skill 与知识库都能自然接入，而不是推翻重来

## 14. 一句话总结

VOIDLAB 当前最合理的软件架构，不是一步做成复杂平台，而是：

**以“前台展示 + 后台运营 + API 中台”为主干，在其上逐步叠加 AI Skill 与知识库能力。**
