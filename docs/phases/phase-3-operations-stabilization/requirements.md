# Phase 3 需求文档

## 1. 阶段名称

运营效率与系统稳定性增强

## 2. 阶段目标

本阶段目标是让系统从“当前业务能跑”升级为“团队能稳定、低风险、标准化地运营”。

这个阶段的重点不是扩展新业务，而是提升当前系统的运营质量和可维护性。

## 3. 背景

Phase 2 完成后，系统已经形成了内容、活动、Builder 和 Leads 的业务闭环。

此时问题会从“能不能做”转变为：

- 运营动作是否标准
- 内容配置是否灵活
- 状态是否清晰
- 系统是否可审计

因此，Phase 3 应聚焦运营稳定化。

## 4. 需求范围

### 4.1 站点配置增强

系统需要支持更完整的站点配置化：

- 首页 Banner 配置
- CTA 配置
- 联系方式配置
- 首页精选区块配置
- 页脚基础配置

### 4.2 状态流完善

对核心对象建立更明确的状态流：

- Article 状态流
- Event 状态流
- Builder 状态流
- Lead 状态流

要求：

- 状态有明确允许的流转方向
- 非法状态变更被阻止

### 4.3 基础权限区分

在现有角色基础上实现基础权限控制：

- Admin
- Editor
- Ops / Sales

要求：

- 不同角色只能访问对应模块
- 不同角色只能执行对应动作

### 4.4 操作日志

系统需要记录关键操作：

- 谁创建了内容
- 谁修改了内容
- 谁变更了 Leads 状态
- 谁发布了活动

### 4.5 基础统计

后台需要提供基础统计看板，至少包含：

- 文章数量
- 活动数量
- Builder 数量
- Leads 数量
- Leads 各状态数量

## 5. 非目标

本阶段不做：

- AI Agent Skill
- 知识库
- 高级 BI 系统
- 自动营销编排
- 复杂审批流引擎

## 6. 用户与角色

### 6.1 Admin

可访问全部模块，拥有全部管理权限。

### 6.2 Editor

管理内容、活动、Builder 和部分配置。

### 6.3 Ops / Sales

主要跟进 Leads，查看统计，不编辑核心内容。

## 7. 核心业务要求

### 7.1 配置化要求

前台中需要高频调整的展示信息，尽量由后台配置，而不是继续手改代码。

### 7.2 审计要求

关键业务动作必须可追踪，尤其是：

- 发布
- 上下架
- 状态变更
- Leads 跟进

### 7.3 稳定性要求

系统应支持团队持续运营，不因单人手工操作而频繁出错。

## 8. 验收标准

1. 首页关键区块可由后台配置
2. 核心对象状态流清晰且可控
3. 基础角色权限已生效
4. 关键操作有日志记录
5. 后台可查看基础统计信息

## 9. 输出物

本阶段完成后应至少产出：

- 配置化后台能力
- 权限控制
- 操作日志
- 基础统计页
- Phase 3 设计文档
