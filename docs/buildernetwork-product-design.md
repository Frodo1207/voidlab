# BuilderNetwork 产品与交互设计

版本：v1.0（产品方向评审稿）  
更新日期：2026-10-19  
关联文档：[BuilderNetwork PRD](./buildernetwork-prd.md)

## 1. 文档目的

本文档把 BuilderNetwork 已讨论的产品方向收敛为可评审、可进入设计和开发的产品方案，重点定义产品结构、关键页面、用户流程、申请与联系方式交换规则，以及 MVP 边界。

本文是产品与交互层的当前依据。接口、权限、数据表和系统分层等工程细节以 PRD 为准；两份文档不一致时，先按本文的产品决策修订 PRD，再进入实现。

## 2. 产品定义

BuilderNetwork 是一个以作品证明能力、以合作机会促成连接的协作市场。用户可以展示自己做过的项目，发布正在寻找的合作机会，发现 Builder 或项目，并通过申请审核建立联系。

产品核心不是“自动匹配”，而是让用户能够：

- 看见真实的人、作品和合作机会。
- 清楚表达自己的能力、当前档期与合作诉求。
- 通过带有理由的申请建立联系，而不是直接暴露私人联系方式。
- 在双方授权后交换联系方式，并跟踪申请与合作进展。

### 2.1 两类“项目”必须区分

| 对象 | 产品含义 | 用户动作 | 典型内容 |
| --- | --- | --- | --- |
| 作品（Work） | 已完成、正在做或可展示的项目成果，是能力证明 | 展示、浏览、点赞/留言、查看参与者 | AI 资讯自动分发系统、开源工具、产品 Demo |
| 合作机会（Opportunity） | 现在希望别人加入、承接或共同推进的需求 | 发布、浏览、申请、处理申请 | 寻找前端开发、招募联合创始人、寻找增长顾问 |

发现广场展示精选作品、热门 Builder 和精选合作机会；“找 Builder”和“找项目”承载完整筛选与全量列表。作品不是招聘需求，合作机会也不是作品集。

## 3. 产品原则与范围

### 3.1 产品原则

1. 作品优先于自我描述，尽量让能力可验证。
2. 机会描述具体，至少说清目标、角色、合作方式和预期。
3. 先申请、再审核、后交换联系方式，默认保护个人隐私。
4. 用户状态和项目状态必须清楚、可维护、可追踪。
5. 先建立可信的人工协作闭环，再逐步增加自动化能力。

### 3.2 Agent 与 AI 的产品边界

前台不设置 Agent 聊天框或“自动匹配”主入口。平台通过稳定、开放的 API 和可复用 Skill 支持用户自己的 Agent 搜索、发布和管理信息；Agent 是开放能力与生态接口，不是本阶段的用户界面主角。

### 3.3 一期不做

- 自动替用户决定是否合作或自动泄露联系方式。
- 站内即时聊天、复杂会话系统和消息已读能力。
- 星级评分、交易担保、支付与佣金。
- 复杂推荐算法、自动撮合和 Agent 托管外联。
- 关注关系、公开动态时间线和复杂社交图谱。

## 4. 用户与核心任务

### Builder / 合作者

- 注册并完善职业身份、技能、作品和合作状态。
- 在发现广场展示作品，或进入“找 Builder”被项目方发现。
- 浏览合作机会，提交申请理由并等待对方处理。
- 获得同意后交换双方授权的联系方式。

### 项目发起者 / 需求方

- 发布清晰的合作机会，持续维护招募状态。
- 浏览 Builder、作品和申请者资料。
- 查看申请理由与相关作品，接受或婉拒申请。
- 接受后查看交换授权的联系方式，推进线下沟通。

### VOIDLAB 运营者

- 管理邀请码，处理违规资料、作品和合作机会。
- 维护精选 Builder、精选作品和精选机会。
- 查看申请异常、举报和基本运营数据。

## 5. 信息架构

```text
BuilderNetwork（独立市场壳层，不复用官网 Header）
├── 发现广场
│   ├── 主视觉 / 市场入口
│   ├── 社区作品展示
│   ├── 热门 Builder
│   └── 精选合作机会
├── 找 Builder
│   ├── 搜索与筛选
│   └── Builder 列表 / 个人主页
├── 找项目
│   ├── 搜索与筛选
│   └── 合作机会列表 / 详情
├── 发布需求
├── 我的工作台
│   ├── 个人资料与合作状态
│   ├── 我的作品
│   ├── 我发布的机会
│   ├── 收到的申请
│   └── 我发出的申请
└── 邀请注册 / 登录
```

市场是独立产品壳层。用户从官网进入后使用市场自己的导航，不复用官网 Header；市场内不放“跳回官网”作为主要导航动作。

## 6. 页面与交互设计

### 6.1 发现广场

**目标：** 让新用户快速理解这里有哪些人、作品与机会，并找到下一步动作。

页面模块：

1. 顶部市场导航：发现广场、找 Builder、找项目、发布需求、我的工作台。
2. 主视觉轮播：展示精选项目机会或代表性 Builder，按钮分别进入详情或申请流程。
3. 社区作品展示：以作品卡片呈现封面、标题、作者、摘要、标签、浏览/互动数据。
4. 热门 Builder：展示职业身份、技能、合作状态和代表作品入口。
5. 精选合作机会：展示招募角色、合作方式、预算提示和申请入口。
6. 区块“查看全部”分别进入对应的全量列表，不把用户留在首页。

作品卡片上的互动一期优先做点赞/有帮助和留言。暂不做星级评分，避免在缺乏真实合作记录时形成失真的信誉分。

### 6.2 找 Builder

列表卡片优先回答“这个人做什么、是否可合作、凭什么可信、如何联系”：

- 姓名、职业身份、所在城市或远程状态。
- 技能标签与简短介绍。
- 当前合作状态：开放合作、有限档期、暂不接单；可补充最早可合作时间。
- 代表作品入口。
- “查看主页”和“发起合作”动作。

筛选维度建议：职业/角色、技能、合作方式、地点/远程、当前档期。默认排序先采用最近活跃或资料完整度，后续再根据使用数据优化。

### 6.3 找项目

每条合作机会展示：

- 标题、需求方、目标与简要背景。
- 项目类型、招募角色、技能要求。
- 合作方式、预算范围、周期、远程/地点。
- 发布时间、截止时间、当前状态与申请数量。
- 申请入口和项目详情入口。

筛选维度建议：项目类型、角色、技能、阶段、合作方式、预算、远程与状态。只展示招募中的机会；已暂停或已关闭的机会应明确标识，默认不进入主要结果。

### 6.4 发布需求

建议采用分组表单，降低填写压力，同时确保机会信息可比较。

**必填字段：**

- 需求标题。
- 机会类型：短期合作、长期合作、顾问、全职/合伙等。
- 项目背景与目标。
- 需要的角色或技能。
- 合作方式与远程要求。

**建议填写字段：**

- 预算范围或“暂不公开”。
- 预计周期、开始时间和申请截止时间。
- 项目阶段、交付物或成功标准。
- 希望申请者提供的材料/信息。

发布前提供预览；发布后可以编辑、暂停招募、标记已找到合作者或关闭。不要将“预算面议”作为默认模糊值，允许用户明确选择公开范围、面议或不公开。

### 6.5 邀请制注册

注册入口明确说明“当前仅限邀请码加入”，先验证邀请资格，再建立账户并创建基础 Profile。

**建议表单顺序：**

1. 邀请码。
2. 账户身份验证（邮箱或手机号，具体认证方式待产品确认）。
3. 姓名/常用称呼。
4. 核心职业身份。
5. 一句话职业介绍。
6. 同意服务条款、隐私说明及社区规范。

注册成功后引导用户补充技能、档期、合作方式、个人介绍和首个作品。注册表单保持短小，不要求用户一次填完整份简历。

邀请码规则建议：管理员生成、可配置使用次数和有效期、记录使用者、支持禁用；邀请码不应代替账号身份验证。

### 6.6 我的工作台

工作台按用户任务组织，不只是个人资料编辑页：

- **个人主页：** 编辑职业信息、技能、合作方式、档期和联系方式授权设置。
- **我的作品：** 创建、编辑、预览、发布/下架作品。
- **我发布的机会：** 查看招募状态、申请数量，编辑、暂停或关闭机会。
- **收到的申请：** 查看申请者身份、申请理由、关联作品，接受或婉拒。
- **我发出的申请：** 查看待处理、已同意、已婉拒、已撤回状态。

工作台首页优先显示待处理申请、待完善资料和近期状态，不把运营数据作为首屏重点。

## 7. 申请与联系方式交换

### 7.1 用户申请流程

```text
浏览 Builder / 合作机会
        ↓
提交申请理由 + 相关作品 + 联系方式交换授权
        ↓
接收方查看申请者资料与理由
        ↓
接收方接受 / 婉拒
        ↓ 接受
平台向双方展示各自已授权的联系方式
        ↓
双方在线下继续沟通，并可更新合作进展
```

### 7.2 申请表单

- 申请对象：某个 Builder 或某个合作机会。
- 申请理由：说明为什么联系、能提供什么、希望如何合作；建议限制在 500 字内。
- 关联作品：可选 1–3 个作品，支持不附作品。
- 联系方式授权：申请人明确勾选“对方接受后，向对方展示我选择的联系方式”。
- 反骚扰提示：同一申请对象短期内限制重复申请，用户可以撤回待处理申请。

### 7.3 接收方处理

接收方能看到申请者的公开 Profile、公开作品、申请理由和申请时间。待处理阶段看不到申请人未公开的联系方式。

接收方可以：

- **接受：** 建立已同意的联系关系，并按双方授权范围展示联系方式。
- **婉拒：** 结束申请；不展示双方的私密联系方式。
- **稍后处理：** 保持待处理状态。

接受不是平台代替双方承诺合作，只代表双方同意进入外部沟通。平台不应把“接受申请”误写成“项目已成交”。

### 7.4 联系方式与隐私规则

- 联系方式与公开 Profile 分开存储，默认私密。
- 用户自行选择可交换的字段，例如邮箱、微信号或其他联系方式。
- 联系方式只有在申请人授权且接收方接受后，才向双方授权用户展示。
- 作品、申请理由、联系方式分别控制可见性，不因 Profile 公开而默认公开联系方式。
- 记录申请创建、接受/婉拒、撤回和联系方式访问等关键审计事件。
- 预留举报、拉黑和隐私撤回入口；撤回后停止未来展示，并明确已复制或已被对方获知的信息无法从对方设备中收回。

## 8. 状态设计

### 8.1 Builder 合作状态

| 状态 | 用户可见说明 | 列表筛选 |
| --- | --- | --- |
| `open` | 开放合作 | 是 |
| `limited` | 有限档期 / 某日期后可合作 | 是 |
| `unavailable` | 暂不接单 | 是，默认可隐藏 |

档期状态由用户维护，可设置“最早可合作日期”或预计空档。系统不得根据用户最近登录自动推断其可接单。

### 8.2 申请状态

`pending` 待处理 → `accepted` 已同意 / `declined` 已婉拒；申请人可在处理前改为 `withdrawn` 已撤回。

申请同意后，可附加合作推进状态：`contacted` 已交换联系方式、`discussing` 沟通中、`collaborating` 合作中、`completed` 已完成、`closed` 已结束。该状态是双方的进度记录，不构成交易或履约证明。

### 8.3 合作机会状态

`draft` 草稿、`open` 招募中、`paused` 暂停、`filled` 已找到合作者、`closed` 已关闭、`expired` 已过期。

机会状态与申请状态彼此独立：一个机会可同时有多条申请；机会关闭后保留历史申请记录，但停止新申请。

## 9. 关键对象建议

| 对象 | 责任 | 关键字段示例 |
| --- | --- | --- |
| Account | 登录身份与认证 | `id`、`email/phone`、`status` |
| InviteCode | 注册准入 | `code_hash`、`max_uses`、`used_count`、`expires_at`、`status` |
| Profile | 公开职业身份 | `display_name`、`primary_role`、`headline`、`skills`、`availability` |
| PrivateContact | 私密联系信息 | `profile_id`、`type`、`value_encrypted`、`share_policy` |
| Work | 作品与能力证明 | `title`、`summary`、`cover`、`links`、`tags`、`status` |
| WorkMember | 作品参与关系 | `work_id`、`profile_id`、`role`、`contribution` |
| Opportunity | 合作需求 | `owner_profile_id`、`title`、`roles`、`budget`、`status`、`expires_at` |
| ContactRequest | 申请与审核 | `from_profile_id`、`target_type/id`、`message`、`status`、`contact_consent` |
| ContactExchange | 双方联系方式授权快照 | `request_id`、双方授权字段、`revealed_at`、`revoked_at` |
| WorkFeedback | 作品轻量互动 | `work_id`、`profile_id`、`type`、`content`、`status` |

联系方式交换应在服务端按申请状态和双方授权校验，不依赖前端隐藏字段实现隐私保护。数据库只存储必要信息；联系方式建议加密或采用受控密钥管理。

## 10. API 与 Skill 边界

所有前台、后台和 Agent/Skill 动作统一走 API，不直接访问数据库。

一期 API 能力建议覆盖：

- 邀请码验证与注册。
- Profile 读取、编辑和合作状态维护。
- Work 创建、编辑、发布、下架与互动。
- Opportunity 创建、编辑、发布、暂停、关闭和列表搜索。
- ContactRequest 创建、查询、撤回、接受和婉拒。
- 申请同意后的联系方式读取与授权撤回。

Skill 面向用户自己的 Agent，基于相同 API 提供可复用任务，例如“更新我的档期”“发布一个合作机会”“搜索符合条件的 Builder”“汇总待处理申请”。Skill 不绕过用户授权，不自动接受申请，不在未获双方授权时读取联系方式。

## 11. MVP 范围与验收

### 11.1 MVP 必须跑通

1. 邀请码验证、账户注册和基础 Profile 创建。
2. Builder 资料、技能、合作状态与可合作时间维护。
3. 作品发布、列表/详情展示及与 Builder 的关联。
4. 合作机会发布、筛选、申请与机会状态管理。
5. 申请理由提交、接收方接受/婉拒、申请状态查询。
6. 双方授权后交换联系方式，未接受前不泄露私密信息。
7. 发现广场、找 Builder、找项目、发布需求、我的工作台的核心页面。
8. 管理端邀请码、精选内容与违规下架的最小管理能力。
9. 面向 Skill 的 API 鉴权、权限范围与审计日志。

### 11.2 MVP 验收标准

- 无有效邀请码的用户不能创建市场账户。
- 用户能在工作台创建并发布作品和合作机会。
- 用户能按角色、技能和档期发现 Builder，按类型和状态发现合作机会。
- 申请者能填写理由并关联作品；接收方能在工作台处理申请。
- 待处理或被婉拒的申请无法读取私密联系方式。
- 申请被接受后，仅能看到双方明确授权交换的联系方式字段。
- 用户可以维护档期与机会状态，列表展示与筛选结果一致。
- 管理员可以禁用邀请码、隐藏违规内容并追溯关键操作。

## 12. 核心指标

一期优先看协作闭环质量，不以页面访问量作为唯一成功标准：

- 邀请注册完成率。
- 注册后资料完善率和首个作品发布率。
- 合作机会有效发布率（信息完整、状态仍有效）。
- 申请提交率与申请理由完整率。
- 申请处理率及平均处理时长。
- 接受申请后的联系方式交换完成率。
- 从发布机会到标记“已找到合作者”的转化率。
- 举报率、无效申请率和过期机会比例。

## 13. 待确认项

以下事项不阻塞产品结构，但开始实现前需要确认：

1. 注册使用邮箱验证码、手机号验证码，还是邮箱/手机号加密码。
2. 联系方式首期支持微信、邮箱、手机号中的哪些字段。
3. 作品互动首期是否包含公开留言；建议先做点赞/有帮助和轻量留言，不做星级评分。
4. 邀请码由运营后台生成，还是支持已注册用户邀请；建议 MVP 先由运营生成。
5. Builder 身份是否必须经过人工审核；建议邀请准入后允许先发布，运营可审核/下架。

## 14. 设计交付与实施顺序

当前 HTML Demo 用于验证页面结构与关键交互，不代表最终视觉稿或真实数据实现。进入前端落地前，应按以下顺序推进：

1. 确认第 13 节的账户和联系方式规则。
2. 根据本设计修订 PRD 的对象、API、权限与状态定义。
3. 先实现注册、Profile、Work、Opportunity 和申请/授权数据闭环。
4. 再实现市场页面、工作台及管理端。
5. 本地端到端验证“邀请注册 → 发布作品/需求 → 提交申请 → 接受 → 交换联系方式”。
6. 最后开放对应 API 并交付 Skill 示例。
