# VOIDLAB 五阶段实施路线图

## 1. 路线图目标

本文档用于定义 VOIDLAB 从“前端 Demo 已完成”到“后台可运营、AI Agent 可协作、知识库最终接入”的整体推进计划。

本路线图遵循两个原则：

1. **先把当前业务跑起来，再做智能化增强**
2. **先把人能稳定运营的系统搭好，再让 AI Agent 接管重复运营动作**

因此，知识库不进入前期核心范围，而放在最后一个阶段；AI Agent Skill 也不应一开始就做成主线，而应建立在稳定后台系统之上。

## 2. 总体阶段划分

整体建议拆分为五个阶段：

1. Phase 1：基础后台与核心内容模块上线
2. Phase 2：当前业务闭环跑通，形成第一个业务里程碑
3. Phase 3：运营效率与系统稳定性增强
4. Phase 4：AI Agent 运营 Skill 接入
5. Phase 5：知识库模块与智能运营升级

## 3. 阶段设计总览

| 阶段 | 核心目标 | 关键词 | 是否里程碑 |
| --- | --- | --- | --- |
| Phase 1 | 搭好后台基础骨架 | 登录、CRUD、媒体、基础 API | 否 |
| Phase 2 | 跑通当前业务闭环 | 内容、活动、Builder、Leads | 是 |
| Phase 3 | 提升运营效率和稳定性 | 配置化、状态流、权限、统计 | 否 |
| Phase 4 | 让 AI Agent 可以代运营 | Skill、标准动作、自动化运营 | 是 |
| Phase 5 | 加入知识库模块 | 知识沉淀、检索、Agent 增强 | 是 |

---

## 4. Phase 1：基础后台与核心内容模块上线

### 4.1 阶段目标

先把后台系统从“骨架”变成“可用的后台雏形”，重点不是做复杂能力，而是让后台具备最小运营能力。

### 4.2 范围

建议本阶段完成以下内容：

- 后台登录能力
- 管理员基础账号体系
- 媒体上传模块
- 资讯管理 CRUD
- 活动管理 CRUD
- Builder 管理 CRUD
- 后端基础数据模型
- 前后台基础 API 打通

### 4.3 本阶段不做

- 复杂权限系统
- Leads 完整跟进流程
- 智能运营
- 知识库
- 发布排期和自动化工作流

### 4.4 交付结果

完成后应达到：

- 后台能登录
- 后台能创建和编辑文章
- 后台能创建和编辑活动
- 后台能创建和编辑 Builder
- 能上传封面图和资源
- 前台可以逐步开始读取 API 数据

### 4.5 验收标准

- 非开发人员可以通过后台录入一篇文章
- 非开发人员可以通过后台创建一个活动
- 非开发人员可以通过后台上架一个 Builder
- 上传的图片可用于前台内容展示

---

## 5. Phase 2：当前业务闭环跑通

### 5.1 阶段目标

这是当前最重要的阶段，也是第一个明确业务里程碑。

目标不是“后台能编辑内容”，而是：

**当前网站已有业务能够真实跑起来。**

### 5.2 核心闭环

本阶段重点打通四个闭环：

1. 资讯闭环  
   后台发布 -> 前台展示 -> 用户阅读

2. 活动闭环  
   后台建活动 -> 前台展示 -> 用户报名 / 预约

3. Builder 闭环  
   后台建档 -> 前台展示 -> 用户发起合作

4. Leads 闭环  
   Contact / Event / Builder 外部意向统一进入 Leads

### 5.3 范围

建议本阶段完成：

- Contact 表单入库
- Event 报名 / 预约入库
- Builder 合作发起入库
- Leads 列表页与详情页
- Leads 状态管理
- 前台核心页面全部切 API
- 基础站点配置模块

### 5.4 业务里程碑定义

本阶段交付完成后，可视为：

**VOIDLAB 当前业务正式上线可运营。**

这意味着：

- 前台核心内容不再依赖手改代码
- 活动、内容、Builder 都能由后台运营
- 所有对外意向有统一承接位置
- 团队开始真正运营这个站，而不是维护一个展示型 Demo

### 5.5 验收标准

- 一篇文章从后台发布后能稳定出现在前台
- 一个活动能被创建、发布并收集报名意向
- 一个 Builder 能上架并收到合作意向
- Contact 页提交的信息能进入 Leads
- Leads 可以进行状态流转

---

## 6. Phase 3：运营效率与系统稳定性增强

### 6.1 阶段目标

当业务能跑起来之后，下一步不是立刻做知识库，而是先把运营体系稳定下来。

这个阶段的目标是：

**让系统从“可运营”进化到“好运营、稳运营”。**

### 6.2 范围

建议本阶段完成：

- 站点配置增强
- 首页精选位配置化
- Banner / CTA / 联系方式配置化
- 更清晰的内容状态流
- 更清晰的活动状态流
- Builder 上下架与审核流
- 基础角色权限区分
- 基础统计面板
- 操作日志与审计能力

### 6.3 重点收益

这个阶段最重要的收益不是多了多少新页面，而是：

- 运营动作更标准
- 发布风险更低
- 数据结构更稳定
- 后续 AI Agent 接入更容易

### 6.4 验收标准

- 首页核心区块无需改代码即可调整
- 内容、活动、Builder 都具备明确状态流
- 不同角色能看到自己该操作的部分
- 关键操作可追踪

---

## 7. Phase 4：AI Agent 运营 Skill 接入

### 7.1 阶段目标

这是“人运营后台”向“AI Agent 协助运营后台”升级的阶段。

这个阶段的核心不是做一个泛化 AI 助手，而是做一个：

**能调用后台标准动作、完成明确运营任务的 Agent Skill。**

### 7.2 设计原则

Skill 必须建立在前面三个阶段稳定完成之后，原因是：

- Agent 不能直接操作混乱系统
- Agent 需要明确对象模型和动作边界
- Agent 需要稳定 API 和清晰权限

### 7.3 Skill 的目标能力

建议这个阶段的 Skill 支持以下动作：

- 上传文章
- 编辑文章
- 发布文章
- 创建活动
- 编辑活动
- 上架 / 更新 Builder
- 查询 Leads
- 更新 Leads 状态
- 上传媒体资源

### 7.4 Skill 的依赖条件

为了让 Skill 真正可用，后台需要提前具备：

- 标准 API
- 鉴权机制
- 幂等设计
- 明确字段校验
- 失败回滚或错误提示
- 可审计日志

### 7.5 Skill 的推荐边界

Skill 第一版建议只做“结构化动作”，不要一开始就做“开放式推理型代运营”。

推荐先支持：

- “帮我发一篇文章”
- “帮我上架一个 Builder”
- “帮我创建一个活动”
- “帮我查看最近的新 Leads”

而不是一开始就支持：

- “你自己判断该怎么运营”
- “你自己改站点策略”

### 7.6 本阶段交付结果

本阶段完成后，团队应该可以做到：

- 通过自然语言调用 Skill 完成后台常规录入
- 减少重复录入工作
- 建立 Agent 与后台协同的标准入口

### 7.7 验收标准

- 能通过 Skill 成功创建一篇文章
- 能通过 Skill 成功创建一个 Builder
- 能通过 Skill 成功创建一个活动
- 能通过 Skill 查询并更新 Lead 状态
- 整个过程具备清晰反馈与错误提示

---

## 8. Phase 5：知识库模块与智能运营升级

### 8.1 阶段目标

知识库明确放到最后一个阶段，这是正确的顺序。

因为知识库不是当前网站的上线阻塞项，而是：

**在业务跑稳之后，用于沉淀经验、支持检索和增强 Agent 的智能基础设施。**

### 8.2 知识库的定位

知识库不建议一开始就做成大而全内容平台，而应优先服务这三类场景：

1. 运营知识沉淀
2. 内容资产沉淀
3. Agent 调用与检索增强

### 8.3 建议收录内容

第一版知识库可考虑承接：

- 已发布文章
- 活动回顾
- Builder 资料沉淀
- 社区 SOP
- 运营流程文档
- 对外合作案例
- 常见问题与标准话术

### 8.4 与 Agent 的关系

知识库不是独立孤岛，而应作为 Agent Skill 的增强层：

- Agent 可从知识库检索内容模板
- Agent 可从知识库读取标准运营规则
- Agent 可辅助生成活动介绍、文章初稿、Builder 文案
- Agent 可基于知识库回答后台运营问题

### 8.5 本阶段交付结果

完成后，VOIDLAB 的系统能力将从“可运营后台”升级为：

- 可运营
- 可沉淀
- 可检索
- 可由 Agent 辅助执行

### 8.6 验收标准

- 后台存在独立知识库模块
- 运营内容可进入知识库
- Agent 可基于知识库完成检索与辅助生成
- 知识库不影响当前主业务稳定运行

---

## 9. 五阶段的依赖关系

这五个阶段不是并列关系，而是依赖递进关系：

### Phase 1 依赖

- 当前前端 Demo 已明确业务对象

### Phase 2 依赖

- Phase 1 的后台基础模块和数据结构已完成

### Phase 3 依赖

- 当前业务已真实开始运营

### Phase 4 依赖

- API、后台动作、状态流和权限边界已足够稳定

### Phase 5 依赖

- 当前业务已稳定
- Skill 已具备可执行价值
- 团队开始有持续沉淀知识资产的需求

---

## 10. 项目经理视角下的优先级判断

如果从项目管理角度看，五个阶段里优先级排序应非常清楚：

### 第一优先级

Phase 1 + Phase 2

原因：

- 这是“从 Demo 到业务系统”的关键跨越
- 没有这两步，后面的 Skill 和知识库都没有基础

### 第二优先级

Phase 3

原因：

- 解决系统稳定性与可运营性问题
- 为 Skill 接入创造标准化条件

### 第三优先级

Phase 4

原因：

- Skill 是效率放大器
- 不是业务存在的前提

### 第四优先级

Phase 5

原因：

- 知识库是长期资产，不是当前上线阻塞项
- 适合在主业务稳定后建设

---

## 11. 推荐实施方式

建议实际推进时，不要按“技术模块”拆任务，而要按“业务里程碑”拆任务。

### 里程碑 M1：后台基础可用

对应：

- Phase 1

### 里程碑 M2：当前业务正式跑起来

对应：

- Phase 2

这是第一个真正的业务里程碑。

### 里程碑 M3：系统进入稳定运营期

对应：

- Phase 3

### 里程碑 M4：AI Agent 开始承担部分运营动作

对应：

- Phase 4

### 里程碑 M5：知识资产进入系统化沉淀阶段

对应：

- Phase 5

---

## 12. 一句话总结

VOIDLAB 最合理的推进顺序，不是先做知识库，也不是先做 AI Agent，而是：

**先把当前业务跑起来，形成可运营后台；再把运营标准化；再让 AI Agent 接手结构化运营动作；最后把知识库接进来，形成长期智能资产。**
